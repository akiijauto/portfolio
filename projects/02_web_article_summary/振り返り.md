# 振り返り — Project 02: Web記事要約ツール

## 発生した課題と解決策

### 1. URLを知らないと使えない
**課題:** 既存の機能はURLを直接入力する前提だったため、「〇〇について書かれている記事を要約したい」という
キーワードベースのニーズに応えられなかった。

**解決策:** Project 13（競合調査ツール）で既に実装済みのTavily Search API連携パターン（`_search_tavily`）を
`scraper.search_articles(keyword, max_results=5)` として移植し、`/search` エンドポイントを新設。
検索結果（タイトル・URL・概要）から1件選ぶと、既存の `/summarize`（URL要約）にそのまま渡せるようにし、
新規ロジックを増やさずに既存の要約フローを再利用した。

### 2. `TAVILY_API_KEY` 未設定環境への配慮
**課題:** キーワード検索機能はTavily APIキーが必要だが、既存のURL要約機能はAPIキー不要で動いていた。
検索機能を追加することで、未設定環境でアプリ全体が動かなくなるのは避けたい。

**解決策:** `search_articles()` は `TAVILY_API_KEY` が無い場合に `RuntimeError` を投げるようにし、
`/search` ルートでこれを捕捉して503＋「URLを直接入力してください」という案内文を返すようにした。
URL要約機能（`/summarize`）には影響しないため、既存ユーザーの利用は変わらない。

### 3. AIエラーとフェッチエラーを区別する
**課題:** 従来は `fetch_article` と `summarize` の両方の例外を1つの `try/except` でまとめて
`fetch_failed` を返していたため、Claude側のクレジット残高不足エラーが起きても
「ページの取得に失敗しました」という誤った案内になってしまう。

**解決策:** `/summarize` の `try/except` を2つに分割し、`fetch_article` 失敗時は `fetch_failed`、
`summarize` 失敗時は `shared.utils.handle_ai_error()` を呼んで `ai_error` または
（クレジット残高不足時の）`service_paused` を返すようにした。
