# 振り返り — Project 19: 接客・クレーム対応ロールプレイAI

## 発生した課題と解決策

### 1. リクエスト形式（form vs JSON）の混在設計
**課題:** 初期実装では `/api/reply` で `scenario`/`difficulty`/`staff_message` を `request.form`、
`history`（配列）を `request.get_json()` で受け取る設計にしていたが、フロント側で1回の `fetch()` に
form dataとJSONを混在させるのは不自然で、CSRFヘッダの扱いも複雑になる。

**解決策:** `/api/start`・`/api/reply`・`/api/score` すべてを `request.get_json(silent=True)` に統一。
`shared/csrf_setup.py` を確認したところ、Flask-WTFの`CSRFProtect`は`X-CSRFToken`ヘッダをチェックするため
JSONボディでもCSRF保護が機能することを確認し、フロント側も `fetch()` で `Content-Type: application/json` +
`X-CSRFToken` ヘッダに統一した。

### 2. AI客とスタッフの役割をClaudeのmessages配列にどう割り当てるか
**課題:** ロールプレイ対話をClaude APIの`messages`配列に渡す際、「客」役をAIが演じるため、
通常の「assistant=AI、user=人間」という対応関係が直感とずれる（AIが演じる客の発言を`assistant`、
スタッフの発言を`user`として扱う必要がある）。

**解決策:** `_history_to_messages()` で `speaker == "customer"` を `assistant`、`speaker == "staff"` を `user`
にマッピングするヘルパーを用意。systemプロンプトで「常に客として話す」ことを明示し、
役割の混乱を防いだ。

### 3. 難易度・シナリオごとの「客の人物像」のプロンプト設計
**課題:** 5シナリオ×2難易度の組み合わせで、AI客の口調や納得しやすさが大きく変わるため、
シナリオごとに個別のプロンプトを書くと管理が煩雑になる。

**解決策:** `SCENARIOS`辞書に業種・シチュエーション・人物像（persona）を、`DIFFICULTIES`辞書に
難易度別の態度の説明を分離して定義し、`_system_prompt()`で両者を組み合わせてsystemプロンプトを
動的に生成する設計とした。新シナリオ・新難易度の追加が辞書への追記のみで完結する。

### 4. 採点結果の5項目スコアをUIでどう可視化するか
**課題:** Claudeが返す5項目（傾聴・共感／謝罪・誠意／説明の分かりやすさ／提案・解決力／言葉遣い・態度、
各0〜5点）を、単なる数値の並びとして表示すると一覧性が低い。

**解決策:** 各項目をラベル・プログレスバー・数値（X/5）の3列グリッドで表示し、合計点（X/25）を
大きく上部に表示するレイアウトに統一。良かった点・改善点・より良い対応例は箇条書き・テキストの
カードとして分け、ひと目で「総合評価→詳細スコア→具体的なフィードバック」の順に読める構成にした。
