# 09_daily_bot 振り返り

## 開発中に発生した課題と解決策

### APSchedulerとFlaskの共存
- **課題**: `flask run` で起動するとリローダーが2プロセス起動し、スケジューラーが二重に動いてDiscordへ二重送信された
- **解決**: `app.run(use_reloader=False)` を設定することで1プロセスに固定した

### バックグラウンドスレッドからのFlaskコンテキスト外処理
- **課題**: スケジューラーのスレッド内でFlaskのアプリコンテキストが取れず、`g` オブジェクトや `current_app` にアクセスできなかった
- **解決**: スケジューラーのジョブ関数ではFlaskコンテキストに依存しない純粋な関数（外部API呼び出し・Discord POST）のみを実行するよう設計を分離した

### ログリストのスレッドセーフ化
- **課題**: スケジューラースレッドとFlaskリクエストスレッドが同時にログリストを読み書きすると競合状態になる
- **解決**: `threading.Lock` でログリストへのアクセスを保護した

### 停止依頼が2回とも効かなかった（2026-08-14 調査）
- **課題**: 毎朝08:00のDiscord配信の停止を2回依頼し、2回ともコード修正・commit・pushまで正しく完了していたにもかかわらず、通知が止まらなかった。
  - `508d982`（08-11）自動配信の停止、`78d00e7`（08-12）NHK要約の除外 — **どちらも本番VPSに未反映**だった。
  - VPSの最終 `git fetch` は 07-31、HEADは `a88b9b8` のまま。サービスの最終起動は 08-11 12:29 JST（修正コミットより前）。
- **原因**: VPS上で `git status` が `## main...origin/main`（差分なし）と表示されていたため「反映済み」と誤判定された。
  この表示は**GitHubとの比較ではなく、07-31時点でキャッシュされた古い `origin/main` 参照との比較**であり、
  `git fetch` を実行しない限り更新されない。実際には31コミット遅れていた。
- **併発要因**: 旧 `app.py` はモジュールレベルで `get_scheduler()` / `set_schedule(8, 0)` を実行していたため、
  プロセスが起動するたび08:00の配信が自動で再登録される構造だった。手動でジョブを削除しても再起動で復活する。
- **解決**: VPSで `git pull --ff-only origin main` を実行（`a88b9b8` → `26684ab`）し、サービスを再起動。
  稼働中プロセスの `/api/status` が `{"scheduled": false, "next_run": null}` を返すことを確認した。

#### このアプリのデプロイ確認手順（`git status` を信用しない）

```bash
# NG: キャッシュされた古いorigin/mainとの比較しか見ていない
git status

# OK: 実際のGitHubと照合する
cd /home/debian/ai-dev && git fetch origin main && git log --oneline HEAD..FETCH_HEAD

# OK: 修正コミットが本当に入っているかを直接判定する
git merge-base --is-ancestor <コミットハッシュ> HEAD && echo PRESENT || echo MISSING

# 再起動が修正コミットより後かを確認する
systemctl show aidev-09-daily-bot.service -p ExecMainStartTimestamp --value

# 最終確認は「ファイルの中身」ではなく「稼働中プロセスの挙動」で行う
curl -s http://127.0.0.1:5009/api/status   # scheduled: false なら配信は停止している
```

ファイルが正しくてもプロセスが古いコードをメモリに保持したままの場合があるため、
`grep` でソースを確認しただけで「反映済み」と判断しないこと。
