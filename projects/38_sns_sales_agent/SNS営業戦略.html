1. 結論サマリ（先に読む3分）

週1本の「ハブ記事」だけを人間が承認し、そこから全メディアの投稿・DM・返信の下書きを定期実行エージェントが自動生成する。ユーザーは週2回15分、承認キューで「承認 / 却下 / 微修正」を押すだけ。

論点結論
誰に売るか顧客層を2つに分ける。 層1＝ソフトウェアベンダー（開発リソース提供・立ち上がり数週間・SNSは効かない）、層2＝社労士事務所（エンド直・立ち上がり6ヶ月〜1年・SNS営業の仕組みの主対象）。介護・障害福祉はエンド直では補助金が使えないため見送り、層1のベンダー経由ルートとして記録（§3-5）。
何を作るか既存システムを置き換えず、その周辺の手作業だけを削る小さなツール（記録の下書き生成／転記をなくす連携／提出前チェック）。加えて導入・定着の伴走を価格に含める — 失注理由の上位が技術ではなく「旗振り役がいない」「使いこなせない」だから。35本は看板ではなく「今すぐ触れる実物」という営業上の武器として使う。
主戦場のメディアハブ＝自社サイト記事（SEO資産・canonical所有）。スポーク＝X / note / Threads / ニュースレター。すべて1本のハブから自動生成。
アウトバウンド公開情報（IT導入支援事業者一覧・法人番号API・gBizINFO・補助金採択一覧）からリスト生成 → 公開問い合わせフォーム宛に送信。SNSのDMは自動化せず、下書きまで自動・送信は手動。
自動化の境界SNSプラットフォームのAPI/自動化には依存しない。GitHub Actionsのcron + Claude API + Notion + Discord Webhookだけで、常駐サーバなしに承認ループが回る。
月額コスト約250〜600円（Claude API $1〜3 + X API従量 $0.2程度 + GitHub Actions無料枠）。
期待値層1は数週間で初案件が現実的（エージェント併用なら即）。層2は発信のみなら初受注まで6ヶ月〜1年、発信＋アウトバウンド併用で90日以内に1〜3件の商談発生が上限（推測を含む、後述）。層1で食いつなぎながら層2を育てるのが本戦略の骨格。

2. 前提の訂正 — X APIのFree枠は既に存在しない

ご指定いただいた「Free枠のみ（月1,500投稿相当）」という前提は、2026年9月現在は成立しません。

X APIは2026年2月6日に「Free / Basic / Pro」のサブスクリプション型ティア制を廃止し、従量課金（pay-per-use）へ完全移行しました。新規開発者向けのFreeプラン登録は終了しており、既存のBasic契約も2026年6月1日から従量課金へ自動移行されています。

出典: X API pay-per-usage pricing and credits (docs.x.com 公式) ／ Announcing the Launch of X API Pay-Per-Use Pricing（参照日 2026-09-01）

従量課金の単価と、ここから導かれる設計判断

操作単価設計への影響
投稿の作成$0.015 / 件週3投稿 × 4週 = 月12件で $0.18。実質無視できる。
URL付き投稿の作成$0.20 / 件本文へのリンク添付は13倍のコスト。ただし後述の通りリンクは本文に入れない方がリーチも伸びるため、コストと運用が同じ方向を向く。
投稿の読み取り$0.005 / 件見込み客のつぶやき検索を自動化すると青天井になりうる。今回は採用しない（§7参照）。
DMインタラクション$0.015 / 件そもそも規約上、無差別な自動DMが禁止のため使わない。

採用する方針: Xは「投稿の書き込みのみ」に用途を限定し、月額予算の上限を $3（約450円） に設定する。この枠内で週3投稿・リンクは返信欄（リプライ）に置く運用が収まります。読み取り系（検索・タイムライン取得）は一切使いません。

3. ターゲット市場 — 需要から選ぶ

改訂履歴: 初版は「既存35本に店舗運営系が4本あるから」という手持ちの在庫から市場を選ぶ誤りをしていた。第2版で需要側から選び直し介護・障害福祉を第1候補としたが、その根拠だった補助金は個人開発の受託物が補助対象製品になることは考えられないため成立しない。第3版（本版）では、この制約を織り込んで顧客層を2つに分けて設計する。

3-3. 結論 — 顧客層を2つに分け、チャネルを分ける

「誰に売るか」を1つに決めようとすると失敗する。立ち上がりが速い層と、資産が積み上がる層は別物で、効くチャネルも違うから。

層1：ソフトウェアベンダー層2：社労士事務所（エンド直）
役割短期の収入源。今日から動ける中期の資産。単価と自由度が高い
売るもの開発リソース。特に既存SaaSへのAI機能追加（社内にAI人材を採用できないベンダーの代替）資料回収・督促の自動化、書類作成支援＋導入・定着の伴走
立ち上がり数週間（エージェント登録なら即）6ヶ月〜1年
単価月70〜110万円。ただし中抜き20〜60%初期30〜150万円＋月額保守1〜3万円。中抜きなし
効くチャネルフリーランスエージェント、公開リストからのフォーム営業、勉強会・登壇、GitHub／ZennSNS発信＋コンテンツ＋アウトバウンド
35本のポートフォリオ最も効く相手。 技術責任者はコードと実装を見て判断する「今すぐ触れる実物」として効く
本プロジェクトの仕組み見込み客発掘（§7）のリスト生成だけ流用仕組みの主対象

正直に言うべきこと：ベンダー相手にSNS発信は主軸になりません。

開発会社の技術責任者が外部パートナーを探すとき、見るのはSNSのタイムラインではなくコード・技術記事・登壇資料という一次情報です。実務で効くのは「勉強会・カンファレンスでの直接接触 → GitHub/Zennでの実装力の裏付け → 紹介」という導線で、SNSはその補強材料にとどまります（今回の調査では、技術発信から開発会社経由の受託に至った具体名入りの一次事例は見つかりませんでした＝推測を含みます）。

したがって、本プロジェクトで作るSNS営業の仕組みの投資対効果は、層2（エンド企業）にかかっています。 層1は仕組みの完成を待たず、今すぐ手で動かせます。

3-4. 層1の進め方 — 下請けに落ちないための条件

この売り方の最大のリスクは多重下請け構造です。公正取引委員会の2022年実態調査では最大6次下請けの事例が報告され、SESのマージン率は20〜60%、エンジニアの手取りは発注金額の5〜7割程度、当初見積100が最終契約額50になる事例もあるとされています。

出典: IT-Biz（公取委調査の解説） ／ SES業界note ／ LASSIC（SaaS企業のAI開発委託）

条件内容
契約形態準委任（人月）ではなく請負（機能パッケージ）で受ける。 稼働時間ではなく成果物の価値で値付けする
商流間に代理店・SES会社を挟まない直接契約を優先。エージェントは立ち上げ期の埋め合わせと割り切る（マージン20〜30%）
ポジション「手が足りないときの穴埋め」ではなく「社内で採用できないAI機能の専門枠」として入る。既存SaaSへのAI後付けはデータ設計からのやり直しが必要になることが多く、専門性が効く
継続化納品して終わりにせず、保守・改修の継続契約に接続する。単発で終わると人月の切り売りに逆戻りする
分散1社に依存しない。取引先が1社だと実質的に下請けと同じ交渉力になる

3-5. 介護・障害福祉分野の扱い（記録）

エンド直では狙いませんが、この分野で確認できた事実は将来の判断材料として残します。

  • 2026年度の介護テクノロジー導入支援事業は補助率が最大3/4〜4/5。中小企業のIT投資の最大の障壁であるコストが制度的に外れている数少ない分野
  • ただし補助対象は認定された製品であり、個人開発の受託物がそれになることは考えられない。したがってエンド事業所に直接売る際にこの補助金は使えない
  • 現場の痛みは実在する。介護ソフトのPC導入率は66.2%（入所型80.7%）だが事業所間・医療機関との情報共有ができているのは1〜2割。手書きメモ→記録ソフト→請求ソフト→LIFE提出用と同じ情報を何度も転記している。ICT導入で記録時間は1人1日45分→30〜35分（約30%減）という実測がある
  • 既存ベンダーはNDソフトウェア、ワイズマン、カナミックネットワーク等の中堅〜大手

この分野に関わるとすれば、ルートは層1です。 すなわち認定製品を既に持っているベンダーに対する開発企画・機能追加の提案。相手は販路と認定を持ち、こちらは開発力を出す。補助金の恩恵は製品を通じて間接的に効きます。ただし介護テクノロジーの認定ベンダー一覧は都道府県ごとに分散しており全国一括では取得できないため、宛先リストとしてはIT導入支援事業者一覧の方が実用的です。

出典: 介護経営ドットコム ／ 厚労省 介護分野の文書に係る負担軽減に関する専門委員会 ／ 都道府県の実施状況まとめ

3-6. 層2（社労士事務所）を選ぶ理由

  • 買う理由が制度側から供給される: 社会保険適用拡大（2026年10月に51人以上企業で賃金要件撤廃、2027年10月に36人以上へ）、改正育児・介護休業法（未対応が3〜4割）。顧問先対応の負荷が増える＝事務所の外注動機になる
  • 競合が手薄: freeeは2026年に資料回収機能とAIエージェント版を投入したが、主戦場は税理士向け。社労士事務所向けの同種サービスは検索上ほぼ見当たらない（推測を含む）
  • 決裁が速く、紹介が広がる: 士業事務所の大半は10名以下で所長個人が決裁者。同業ネットワークでの紹介文化が強い
  • 中立ポジションを取れる: 大手ベンダーは自社エコシステム内でしか機能を提供しない。TKC・弥生・紙運用が混在する事務所は取り残されており、どの会計ソフトとも連携できる中立の立ち位置は大手の経済合理性が及びにくい
  • 弱点: 保守的でセキュリティ懸念が強く、営業サイクルが長期化しやすい。名簿は都道府県会ごとに分散しており全国横断の一元検索は確認できなかった。この層が本プロジェクトの成否を左右するため、最初の3ヶ月で反応を実測して継続可否を判断する

3-7. オファー階段（層2向け）

段商品価格ねらい
0公開デモ（既存35本のうち、記録・帳票・OCR・問い合わせ系）無料「動くものを今すぐ触れる」ことで信頼のハードルを下げる
130分の業務棚卸し（どの作業に何分かかっているかを一緒に数える）無料商談化。効果を数字で示す材料をここで作る
2お試し導入（1業務だけ、1週間で動くものを出す）3〜5万円「使いこなせない・定着しない」という最大の失敗要因を小さく試して潰す
3本導入（複数業務・既存ソフト連携・研修込み）30〜150万円本受注
4月額保守（改修・制度変更対応・利用状況レポート）月1〜3万円ストック収益。利用率レポートで「効果が分からない」を継続的に潰す

3-8. 層1のオファー — 「御社の製品に組み込める機能」の提案として送る

層1は「開発を請け負います」という汎用の売り込みではない。相手の製品を調べたうえで「この機能を御社の製品に組み込めます」という具体案を持ち込み、開発担当の一部に入れてもらうという形を取る。

この形にする理由は3つあります。

  • 個別性が担保される。 IT導入支援事業者一覧では各社の登録ITツール名とカテゴリが公開されているため、「御社の◯◯（製品名）に」と名指しで書ける。汎用の営業文とは返信率が変わる（高度な個別化は返信率が約2倍という調査がある）
  • 相手にとって判断が軽い。 「開発を外注するか」は重い決裁だが、「開発担当を1人増やす」「機能を1つ試す」は軽い。入口のハードルを下げる
  • こちらの強みが直接効く。 相手は技術者なので、35本の動くアプリとGitHubがそのまま能力の証明になる。エンド企業のように効果を説明する必要がない

送信先とチャネル

SNSは使いません。各社が自社サイトに公表している会社メールアドレス／問い合わせフォーム宛に送ります。 公表されたアドレスへのBtoB連絡であり、オプトアウト導線と送信者情報を明記する点は層2と同じです（§10）。

文面の構造

[件名]   {相手の製品名} に{機能名}を組み込むご提案
[冒頭]   {登録ITツール名／製品カテゴリ}を拝見しました ← 出典URL必須。ここが個別化の本体
[提案]   その製品カテゴリに対して有効なAI機能を「1つだけ」具体的に
         例: 会計系なら証憑の欠落検知、受発注系ならFAX/PDFからの自動起票
[証拠]   類似機能を実装済みのデモURL 2〜3本 ＋ GitHub
[立場]   「外注先」ではなく「開発担当の一部として参画したい」
         まず小さい機能1つから、機能単位でお受けする旨
[CTA]    30分の技術的な打ち合わせ（1通1目的）
[署名]   氏名・屋号・サイトURL・配信停止の導線

入口の柔らかさと、契約の固さは分けます。 メッセージは「開発担当の一部に混ぜてください」という入りやすい形にしますが、契約は機能単位の請負に寄せます（§3-4）。ここを曖昧にしたまま「開発チームの一員」として稼働時間で入ると、そのまま人月の準委任になり、単価が相手の予算で決まってしまうためです。入口は柔らかく、契約は成果物単位で。

3-9. メッセージの型（層2）

層2（社労士事務所）向け:「顧問先からの資料回収と督促に、月何時間使っていますか。社会保険の適用拡大が2026年10月に、2027年10月にもう一段来ます。いま手作業で回している部分を、30分の棚卸しで洗い出しませんか。1業務・1週間・3万円から試せます。会計ソフトはfreeeでもTKCでも弥生でも構いません。」

層2は削れる分数から入り、層1は相手の製品に足せる機能から入る。相手が何で判断するかが違うためです。

4. メディア構成 — 逓増しないハブ&スポーク

4-1. 構造

   ├─ スポーク: Threads     （200字未満・会話誘発型）
   ├─ スポーク: ニュースレター（3行サマリ＋CTA）
   └─ スポーク: (将来追加)   ← capabilities設定1行 + アダプタ1クラスで済む

SNS投稿はハブになれません。 プラットフォーム側がcanonicalの所有権を持たないため、SEO資産が自分の手元に残らないからです。noteやMediumへ全文転載する場合のみ rel=canonical をハブへ向ける必要があります（SNS本文の重複はGoogleの検索評価にはほぼ影響しません）。

4-3. 「メディア数に逓増しない」ことを担保する設計原則

  1. 差分はコードでなくデータに寄せる。 文字数上限・メディア形式・リンク可否・ハッシュタグ可否は capabilities としてJSON化し、if分岐を作らない。
  2. アダプタは1インターフェース1クラス。 新規媒体の追加が「1ファイル＋設定追加」で完結しない場合、それは設計が崩れた兆候としてレビューで弾く。
  3. 配信結果は媒体単位で独立管理。 1媒体の失敗が他媒体の成功を巻き込まない（DeliveryAttempt を post × integration の粒度で持つ）。
  4. 承認は媒体ごとに行わない。 ハブ1本の承認で全スポークが確定する。ここが「ユーザー負担がメディア数に比例しない」ことの本体。

参考実装: Postiz（33プロバイダを SocialAbstract 基底クラスで抽象化）／ Mixpost（SocialProviderManager による契約点方式）

5-2. なぜ Discord のボタンで承認しないのか

Discordのボタン（コンポーネント）は、通常のIncoming Webhookから送るとエラーも出ないまま表示されません（アプリケーション所有のWebhookのみ対応）。さらにボタンのクリックを受け取るには公開HTTPSのInteractions Endpointが必須で、常駐サーバが要ります。

したがって Discordは「通知＋リンク型ボタン（URLへ飛ばすだけ）」に限定し、実際の承認操作はNotionページ上のボタンプロパティで行います。これで常駐サーバなし・cronのみで承認ループが閉じます。

出典: discord-api-docs Discussion #6990 ／ Notion API Request limits（平均3req/秒・15分あたり2,700コール、全プラン共通）

8-4. 生成パイプラインと品質ゲート

全文をLLMにゼロから書かせません。可変域を「冒頭の1〜2文」だけに絞るのが誇張・事実誤認を防ぐ核心です。

① 企業の公開情報 → 「ファクトシート」を構造化データとして抽出（出典URLを必ず紐付け）
② ファクトシートから「個別化に使える一文」の候補を複数生成 ← 出典なしの候補は破棄
③ 定型テンプレート ＋ 選ばれた1文 を結合
④ 品質ゲート（下記）を通過したものだけを承認キューへ

自動で弾く条件:

  • 出典URLが紐付いていない個別化文（ハルシネーション対策の最重要ゲート）
  • 数値・固有名詞（社名・金額・役職・日付）がファクトシートと完全一致しない
  • 禁止語リストへのヒット（「業界No.1」「必ず」「絶対」「〜だけで解決」など景表法リスク表現）
  • 競合の誹謗・比較優良表示
  • 過去に同一企業へ送った文面との類似度が閾値超（コピペ感の温床）
  • 文字数がレンジ外／配信停止導線の欠落

一次判定はルールベース（正規表現・辞書照合）＋ Haiku での軽量判定の二段構成とし、最終承認は必ず人間が行います。

9. 自動返信（返信トリアージ）の仕組み

「自動返信」は完全自動送信にしません。 分類と下書き生成までを自動化し、送信は1クリック承認とします。初期運用で自動送信を許すと、誤爆した1通が信用を毀損するコストの方が、節約できる数十秒より大きいためです。

9-1. 分類スキーマ

{
  "message_id": "string",
  "category": "interested | needs_conditions | not_now | follow_up_later | spam",
  "confidence": 0.0-1.0,
  "key_signals": ["判断根拠となった文言"],
  "suggested_followup_date": "YYYY-MM-DD | null",
  "draft_reply": "返信下書き",
  "requires_human_review": true/false
}

安全側の固定ルール:

  • confidence < 0.85 なら無条件で requires_human_review = true
  • interested / needs_conditions（＝商談・金額に触れうる）は confidence によらず常に人間レビュー＋Discord即時通知
  • spam の自動アーカイブは confidence > 0.95 のときのみ

9-2. 失敗モードと対策

失敗モード対策
誤ってスパム分類し、商談機会を失う低confidence・境界カテゴリは必ず人間キューへ。自動アーカイブは高confidenceのみ
誤送信（宛先違い）承認ボタン押下の直前に宛先とスレッドを再表示。初期は自動送信を完全にオフ
承認待ちの滞留でSLA（返信速度）を落とすinterested のみDiscordでモバイル通知し、数分以内の承認を促す。他は週次バッチで十分
カテゴリの意味的重複で判断に迷うkey_signals に根拠文言を出させ、人間が3秒で判断できるようにする

10. 法令・規約のレッドライン

※以下は公開情報の調査結果であり、法的助言ではありません。実運用の前に必要に応じて専門家にご確認ください。

10-1. 特定電子メール法（メール送信）

2008年改正により、広告・宣伝目的のメールは事前同意（オプトイン）が原則です。ただし法律上、「自己の電子メールアドレスを公表している団体、または営業を営む個人」はオプトイン規制の対象外とされています。企業がサイトに公開している問い合わせ窓口・代表メールへのBtoB営業は、この例外に該当しうる形です。

採用する運用: 送信先は「公開されている法人の問い合わせフォーム／公表メールアドレス」に限定する。個人名に紐づくアドレスは使わない。すべての送信文に配信停止（オプトアウト）の導線と送信者の氏名・連絡先を明記する。

出典: 総務省 特定電子メール法 ／ 総務省ガイドライン(PDF)

10-2. 個人情報保護法

法人の代表番号・問い合わせ窓口メールなど個人に紐づかない情報は個人情報に該当しない可能性が高い一方、名刺やSNSから得た個人名付きの情報をデータ化・リスト化すると個人情報として規制対象になり、利用目的の特定・通知義務が生じます。今回のリストは法人単位の公開情報に限定し、個人名は含めません。

12-3. 期待値の現実（楽観しないこと）

  • 「発信のみ」で初受注に至るのは早くて3ヶ月、平均的には6ヶ月〜1年。
  • 「発信＋アウトバウンド」併用なら1〜2ヶ月で最初の面談が発生する可能性が明確に高まる（定量データなし・推測）。
  • 90日終了時点の現実的な見込みは、商談1〜3件・受注0〜1件（推測。根拠となる定量調査は確認できませんでした）。
  • 最大のリスクは市場ではなく継続の断念です。ブログ領域の類推では3ヶ月で約7割が離脱します。だからこそ「週30分の承認だけ」に運用負荷を落とす設計が、戦略の本体です。

12-4. 撤退・方針転換の判断基準

  • 90日: 層2で問い合わせ・DMがゼロなら、投稿内容ではなく「能動的接点の不足」を疑い、アウトバウンドの送信数を倍にする。層1で1件も受注できていない場合は、単価の設定か見せ方（GitHub・ポートフォリオの技術者向けの整え方）を疑う。
  • 180日: エンゲージメント（保存・返信・DM）自体が伸びていないなら、ターゲット設定か投稿の型そのものを見直す。層2が育たないまま層1だけで回っているなら、それは「SNS営業の仕組みが不要だった」というシグナルであり、仕組みへの追加投資を止めて層1に集中する判断もあり得る。
  • 返信率が2%を下回る: 文面ではなくリストの質（スコアリングの特徴量）を先に疑う。50件以下の厳選が1,000件超の2.8倍という数字は、リスト精度の重要性を示しています。
  • 12ヶ月: アウトバウンドも試して受注ゼロなら、発信媒体・専門テーマの再選定を検討する。

13. やらないと決めたこと

やらないこと理由
YouTube・ショート動画制作は自動化できるが、「投稿→受託」の転換を裏付ける日本の一次事例が確認できず、コメント対応・信頼構築の人的工数が自動化できない。ROI未検証のまま本格投資しない
LinkedInの本格運用日本の登録者約500万人はIT/コンサル/外資に偏り、店舗オーナー層に届きにくい。無料枠は週80〜100件の申請上限＋パーソナライズ招待月5件程度と制約が厳しい。自動化は明確な規約違反
SNS上の課題つぶやき自動検索X APIの読み取り従量課金が青天井。スクレイピング・ミラーは規約違反。週5分の手動確認で代替
クラウドソーシングの新着案件自動監視規約でスクレイピングが禁止されている可能性が高い。各社のメール新着通知で代替し、提案文の下書き生成だけを自動化する（こちらは規約上問題なく、費用対効果が高い）
Facebookグループでの営業40〜60代経営者への到達チャネルとしては有利だが、グループ規約で宣伝・勧誘が禁止されるケースが多く、成果は人的な関係構築に依存して自動化できない。第2フェーズ以降の検討事項とする
建設業・不動産業への参入需要はあるが、建設はANDPAD（21万社・55万人）、不動産はいえらぶCLOUD（4.4万社）が業界標準として普及済み。個人が正面から入る市場ではない
税理士事務所向けの資料回収ツール痛みは大きい（確定申告期の残業が閑散期の2.4倍）が、freeeが2026年7月に資料回収機能、8月にAIエージェント版を投入済み。大手が会計ソフト契約に抱き合わせてくる速度に飲み込まれる
勤怠・給与・会計・請求・電子契約の新規開発freee／マネーフォワード／SmartHR／ジョブカンが低価格〜無料枠まで押さえている。法改正への追従コストを個人が負い続けるのは非現実的
大企業向けAIエージェントの本番導入単価は月100〜500万円級と最も大きいが、PoCを実施した企業のうち本番稼働に至るのは1〜2%という調査がある。調達もSIer前提
介護保険請求・LIFE本体との連携機能3年ごとの報酬改定への追従コストを個人が負い続けられない。エクスポートまでで止める
Instagram / Threads の自動DM規約違反。Threadsは公式API経由の投稿のみ採用
返信の完全自動送信誤爆1通の信用毀損コストが、節約できる数十秒を上回る

13-1. 第2フェーズ以降の検討候補（今回は着手しない）

  • 公的支援機関ルート: よろず支援拠点のコーディネーター（日当27,500円・都道府県ごとに毎年度公募）、商工会議所のエキスパートバンク登録、デジタル化・AI導入補助金のIT導入支援事業者登録（法人単独またはコンソーシアム）。いずれも受動的な案件供給だが、単価と信用力が高い。公募情報の週次ウォッチは③のエージェントに追加するだけで済むため、費用対効果は良好
  • Qiita / Zenn への技術記事転載: 読者はエンジニア中心で直接の発注者ではないが、企業内エンジニア経由の紹介が期待できる。既存GitHubリポジトリ（README・PR差分・Issue）から「課題→設計→実装→学び」の骨子を自動生成できるため、スポークに追加する追加コストは小さい。ただし両サービスとも宣伝目的の投稿は規約で制限されるため、導線はプロフィール欄と記事末尾の固定文言に限定する
