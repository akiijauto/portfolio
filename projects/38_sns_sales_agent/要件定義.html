要件定義 — Project 38: SNS営業支援エージェント

作成日: 2026-09-01 ／ ステータス: 設計フェーズ（実装は次フェーズ）
戦略の全体像と根拠は SNS営業戦略.html を参照。

1. 背景と目的

受託案件および月額保守契約を継続的に獲得する。ターゲット市場は手持ちの資産からではなく需要側から選定し、第1ターゲットを介護・障害福祉事業所、第2候補を社労士事務所とする（選定根拠は SNS営業戦略.html §3）。Flask製の業務自動化Webアプリ35本（ai-l-a-b-o.com）は看板ではなく「今すぐ触れる実物」という営業上の武器として用いる。

ただし、営業活動そのものが定型作業の反復でユーザーの時間を奪っては本末転倒となる。したがって本プロジェクトの最上位の要件は「ユーザーの作業を判断のみに限定し、その負担が露出メディア数に比例して増えないこと」である。

2. スコープ

2-1. 対象に含むもの

  • 定期的な外部発信（ハブ記事1本から複数メディアへの自動展開）
  • 見込み客の発掘（公開情報からのリスト生成とスコアリング）
  • DM／問い合わせフォーム向け送信文の自動生成
  • 受信メッセージの自動分類と返信下書きの生成
  • 上記すべてを束ねる承認キューと通知

2-2. 対象に含まないもの

  • SNSへの自動DM送信、自動フォロー、自動いいね（各社規約違反のため）
  • ブラウザ自動化による投稿・データ取得（同上）
  • 返信メッセージの完全自動送信（人間の承認を必須とする）
  • 動画メディア（YouTube／ショート）の運用
  • LinkedInの本格運用

3. 機能要件

FR-1: ネタ収集エージェント（週次）

  • git log（--since で前週分）、GitHub Releases、Notionの開発記録を取得する
  • コミットを Conventional Commits 形式で分類し、「詰まり→解決」のペア、リリース、数値変化を検出する
  • 検出内容を「Before/After型」「進捗報告型」「数字公開型」に分類し、ハブ記事の骨子を3案生成する
  • 結果を Notion「投稿候補」DB へ status=承認待ち で登録し、Discord へ通知する

FR-2: 配信エージェント（週次）

  • 承認済みのハブ記事を取得し、capabilities 設定に従って媒体別の投稿を生成する
  • 対応媒体: X（100字未満・本文リンクなし）、note（全文転載＋rel=canonical）、Threads（200字未満）、ニュースレター（3行サマリ＋CTA）
  • 生成物を Notion「配信キュー」DB へ status=承認待ち（リスクタグ=低）で登録する
  • 次回実行時に status=承認済み を検知し、X APIでの投稿・note下書き作成・ニュースレター下書き作成を実行する
  • 配信結果は post × integration の粒度で記録し、1媒体の失敗が他媒体を巻き込まないこと

FR-3: 見込み客発掘エージェント（週次）

  • 介護サービス情報公表システム（第1ターゲットの母集団）、国税庁 法人番号Web-API、gBizINFO API、デジタル化・AI導入補助金の交付決定事業者一覧から候補事業所を取得する
  • 特徴量（サービス種別・定員規模・補助金採択歴・運営法人の事業所数・所在地）でスコアリングし、上位20社に絞る
  • 法定公表制度のデータは事業所の特定と母集団の把握までに用途を限定する。公表された電話番号への架電には用いず、接触は各事業所が自社サイトに公開している問い合わせフォーム宛に限る（制度趣旨との整合のため）
  • 各社の公開情報からファクトシートを構造化抽出し、出典URLを必ず紐付ける
  • 定型テンプレートに「個別化された冒頭1〜2文」のみを差し込む形で送信文を生成する
  • 結果を Notion「営業リスト」DB へ status=承認待ち（リスクタグ=高）で登録する

FR-4: 返信トリアージエージェント（日次×2）

  • 受信箱・問い合わせフォームの新着を取得する
  • interested / needs_conditions / not_now / follow_up_later / spam の5分類と confidence、判断根拠 key_signals、返信下書きを生成する
  • confidence < 0.85、または interested / needs_conditions の場合は requires_human_review=true を強制する
  • spam の自動アーカイブは confidence > 0.95 の場合のみ許可する
  • interested は Discord へ即時通知する（返信速度が成約率に直結するため）

FR-5: 承認キュー

  • 1件の表示要素: 提案内容（最上部）、リスクタグ、影響範囲（送信先・公開日時・媒体）、経過時間と失効期限、根拠（折りたたみ）
  • 操作は 承認 / 却下 / 微修正 の3択のみ。微修正は本文が事前入力された状態で開き、編集後も1ボタンで確定する
  • 一括承認はリスクタグ=低の項目に限定し、対象件数と最大影響を確認モーダルに表示する
  • 72時間で自動失効する
  • 却下・微修正の履歴を記録し、後続のスコアリング閾値調整に用いる

FR-6: 品質ゲート（送信前の自動チェック）

以下のいずれかに該当する生成物は承認キューに載せず破棄またはフラグ付けする。

  • 出典URLが紐付いていない個別化文
  • 数値・固有名詞がファクトシートと完全一致しない
  • 禁止語リストへのヒット（「業界No.1」「必ず」「絶対」「〜だけで解決」等）
  • 競合の誹謗・比較優良表示
  • 同一企業への過去送信文との類似度が閾値超
  • 文字数がレンジ外、または配信停止導線の欠落

4. 非機能要件

ID要件受入基準
NFR-1ユーザーの作業時間承認業務の合計が週30分以内。1件あたり低リスク5〜15秒、要文脈確認30〜60秒
NFR-2メディア追加コストの非逓増新規媒体の追加が アダプタ1クラス ＋ capabilities設定の追加のみで完結すること。コアやスケジューラの改修を要する場合は設計違反として差し戻す
NFR-3ランニングコスト月額600円以内（Claude API・X API・その他すべて込み）
NFR-4常駐サーバ不要GitHub Actions の cron のみで承認ループが閉じること。VPS・常駐プロセスを前提としない
NFR-5規約遵守SNSの自動DM・自動フォロー・ブラウザ自動化・スクレイピングを一切実装しない
NFR-6法令遵守送信先は公開されている法人の問い合わせ窓口／公表メールに限定。全送信文にオプトアウト導線と送信者情報を明記
NFR-7LLMコスト効率プロンプトキャッシュ（tools→system→messages の順序遵守）、Batch API（レイテンシ不要処理）、モデル階層化（分類=Haiku／生成=Sonnet）を実装すること
NFR-8削除の禁止エージェントは既存ファイル・データを削除しない。不要判定は「アーカイブ」ステータスへの変更に留める

8. 実装方針の決定事項

  • スケジューラはAPScheduler ではなく GitHub Actions に寄せる。 常駐プロセスが不要になり、hub_app.py の多重起動問題も回避できる。VPS費用もゼロ
  • Publicリポジトリで運用する（Actions無料枠が無制限のため）。秘匿情報はすべて Secrets に置き、コードにも成果物にも残さない
  • DBは Notion を正とし、ローカルSQLiteはキャッシュ・冪等性確保のためだけに用いる

9. 受入テスト

#観点方法
T-1機能テスト各エージェントを workflow_dispatch で手動起動し、Notionの各DBに想定どおりのレコードが作られること。品質ゲートが禁止語・出典なし文面を確実に弾くこと（意図的に不正な生成物を注入して確認）
T-2ブラウザ実行テスト承認画面（Notionページおよび自前UIを用意する場合はそのUI）を実ブラウザで開き、承認／却下／微修正の3操作とモバイル表示を確認する
T-3冪等性同一cronを2回連続実行し、二重投稿・二重登録が起きないこと
T-4部分失敗1媒体の認証を意図的に失効させ、他媒体の配信が成功すること・partial_failed が記録されることを確認
T-5コスト1ヶ月の実運用後、API利用額が NFR-3 の範囲内に収まっていることを実測
T-6作業時間4週間の運用で、週あたりの承認作業時間が30分以内に収まっていることを実測
