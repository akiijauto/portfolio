1. これは何か

SNSと公開情報を使った新規顧客獲得を、ユーザーの作業を「週2回15分の承認」だけに圧縮して回すための仕組みです。4体のエージェントが GitHub Actions の定期実行で動き、投稿・DM・返信の下書きを作り、Notionの承認キューに積み、Discordで知らせます。

SNSプラットフォームの自動DMやブラウザ自動化には一切依存しません（各社の規約違反となるため）。

3. セットアップ手順

手順1: リポジトリの準備

git clone https://github.com/akiijauto/portfolio.git
cd portfolio
pip install -r requirements.txt

GitHub Actions の無料実行枠が無制限になるため、Publicリポジトリでの運用を前提としています。Privateの場合は月2,000分の枠を消費します。

手順2: 環境変数の設定

ローカル検証用は .env、本番（GitHub Actions）用はリポジトリの Settings → Secrets and variables → Actions に登録します。

NOTION_TOKEN=...
NOTION_DB_POST_CANDIDATES=...   # 投稿候補DB
NOTION_DB_DELIVERY_QUEUE=...    # 配信キューDB
NOTION_DB_PROSPECTS=...         # 営業リストDB
NOTION_DB_REPLY_QUEUE=...       # 返信キューDB
DISCORD_WEBHOOK_URL=...
ANTHROPIC_API_KEY=...
AI_PROVIDER=anthropic
TWITTER_API_KEY=...
TWITTER_API_SECRET=...
TWITTER_ACCESS_TOKEN=...
TWITTER_ACCESS_TOKEN_SECRET=...
X_MONTHLY_BUDGET_USD=3          # 支出上限（超過時はエージェントが投稿をスキップし通知のみ行う）
HOUJIN_BANGOU_APP_ID=...
GBIZINFO_TOKEN=...

セキュリティ上の遵守事項

  • .env は .gitignore に含まれていることを必ず確認してからコミットすること
  • APIキーをコード・ログ・Notionのページ本文・Discordの通知文に出力しないこと（shared/notify.py はWebhook URLをマスクする実装になっている）
  • X APIは従量課金のため、開発者ポータル側でも支出上限（spend limit）を設定すること。環境変数側の上限だけに頼らない

手順3: Notion データベースの作成

以下4つのDBを作成し、インテグレーションに接続権限を付与します。各DBの必須プロパティは 要件定義.html §5-2 を参照してください。

  1. 投稿候補 — ハブ記事の骨子案が溜まる場所
  2. 配信キュー — 媒体別の投稿下書きが溜まる場所
  3. 営業リスト — 見込み客とDM文面が溜まる場所
  4. 返信キュー — 受信メッセージの分類と返信下書きが溜まる場所

各DBに「ステータス」プロパティ（承認待ち / 承認済み / 却下 / 失効 / 送信済み）と、承認・却下を行うボタンプロパティを設置します。承認操作はNotion上で行います（Discordのボタンは通常のWebhookでは表示されないため、Discordは通知とリンクの提示に徹します）。

手順4: 定期実行の設定

.github/workflows/ に以下を配置します。時刻はUTC基準のため、JSTから9時間を引いた値を指定します。

ワークフローcron（UTC）JST
ネタ収集17 18 * * 0月曜 03:17
配信17 0 * * 1月曜 09:17
見込み客発掘17 18 * * 2水曜 03:17
返信トリアージ17 23,9 * * *毎日 08:17 / 18:17

各ワークフローに必ず以下を含めます。

on:
  schedule: [{ cron: '17 18 * * 0' }]
  workflow_dispatch:          # 手動実行での検証用
concurrency:
  group: sns-agent-collect
  cancel-in-progress: false   # 二重起動の防止

なぜ分を :17 にずらすのか: 毎時0分付近はGitHub Actions全体の負荷が高く、scheduleイベントが遅延したりドロップされることがあるためです。

60日ルール: リポジトリに60日間活動がないと schedule は自動停止します。本設計では各エージェントが実行結果（配信ログ・スコアリング結果）をリポジトリへコミットするため、この活動が自動的に発生し停止を防ぎます。

手順5: 動作確認

  1. 各ワークフローを workflow_dispatch から手動実行する
  2. Notionの各DBに status=承認待ち のレコードが作られることを確認する
  3. Discordに通知が届き、リンクからNotionページへ遷移できることを確認する
  4. ブラウザでの実行テスト: PCとスマートフォンの実ブラウザで承認画面を開き、承認・却下・微修正の3操作が想定どおり動作することを確認する
  5. 同じワークフローを2回連続で実行し、二重登録・二重投稿が起きないことを確認する
  6. X APIへの実投稿は、最初はテスト用アカウントで1件だけ行い、課金額を開発者ポータルで実測してから本番運用へ切り替える

4. 日々の使い方

タイミングやること所要
月曜 朝Discord通知 → Notion「投稿候補」でハブ記事の骨子3案から1案を承認（必要なら微修正）10分
火曜 朝Notion「配信キュー」で媒体別の投稿を一括承認3分
水曜 朝Notion「営業リスト」で送信先を選び、文面を承認 → 送信15分
随時Discordに「高温度リード」の通知が来たら返信下書きを承認1件2分

合計 週30分以内に収まらない場合は、承認画面の情報設計に問題があるサインです。振り返り.html に記録してから改善してください。

5. 運用上の禁止事項

  • ブラウザ自動化ツール（Selenium / Playwright）でSNSにログインして投稿・DM・フォローを行わないこと。全媒体で規約違反であり、2026年は警告なしのアカウント停止事例が確認されています
  • SNSの自動DM送信機能を追加しないこと
  • 返信の完全自動送信を有効化しないこと
  • クラウドソーシング各社の案件一覧をスクレイピングしないこと（メールの新着通知を使うこと）
  • 営業メールの送信先を、個人名に紐づくアドレスへ広げないこと。公開されている法人の問い合わせ窓口・公表メールに限定すること
  • 送信文からオプトアウト（配信停止）の導線と送信者情報を外さないこと
  • エージェントによるファイル・データの削除を実装しないこと。 不要判定は「アーカイブ」ステータスへの変更に留めること

6. トラブルシューティング

症状原因と対処
定期実行が突然止まった60日間リポジトリに活動がなく schedule が無効化された可能性。Actionsタブから手動で再有効化し、コミットが毎回発生しているか確認する
投稿が二重に行われたconcurrency 設定の欠落。前回ジョブの遅延と重なった可能性。cancel-in-progress: false とグループ名を確認する
Notion APIが429を返すレート制限（平均3req/秒・15分あたり2,700コール）。ページング処理に待機を挟み、last_edited_time による差分検知で取得件数を減らす
Discordのボタンが表示されない仕様です。通常のIncoming Webhookではコンポーネントが表示されません。リンク型（URLへ遷移するだけ）のボタンのみ使用してください
X APIの請求が想定より多い本文にリンクを含む投稿は $0.20/件（通常の13倍）です。リンクは返信欄に置く運用に戻してください。読み取り系エンドポイントを使っていないかも確認
Claude APIのキャッシュが効かないresponse.usage.cache_read_input_tokens が0のままなら、プロンプトの先頭付近にタイムスタンプ等の可変値が混入している可能性。順序は tools → system → messages で固定し、可変情報は最後尾へ。最小トークン数（Haiku 4.5は4,096）未満だとエラーも出ずキャッシュされません
DM文面に事実誤認が混じる品質ゲートの「出典URL紐付けなしは破棄」が機能しているか確認。個別化する範囲を冒頭1〜2文に絞り、全文生成に戻していないか確認
