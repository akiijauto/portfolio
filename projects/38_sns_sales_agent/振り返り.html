振り返り — Project 38: SNS営業支援エージェント（設計フェーズ）

作成日: 2026-09-01 ／ フェーズ: 戦略立案・設計
この文書は「何が起きて、なぜ困り、どう解決したか」を、次に同種の設計をするときに読み返せる形で残すものです。

このフェーズでやったこと: Sonnetエージェント28体で並列Web調査を行い、Opusが統合してSNS営業戦略と運用設計をまとめた。実装はまだ行っていない。

設計中に見つかった課題と、その解決

課題 1前提の崩壊

「X APIのFree枠で運用する」という前提が、そもそも成立しなかった

何が起きたか: 当初「Free枠（月1,500投稿相当）だけで投稿を自動化する」方針で設計を始めた。ところが調査の結果、X APIは2026年2月6日にティア制を廃止して従量課金へ完全移行しており、Freeプランの新規登録は終了、既存のBasic契約も6月に従量課金へ自動移行済みだった。

なぜ困ったか: 「無料枠の範囲で回す」という制約を土台に投稿頻度やメディア構成を組んでいたため、土台ごと作り直しになりかねなかった。

どう解決したか: 従量課金の単価を調べ直したところ、投稿1件 $0.015、URL付き投稿は $0.20 だった。週3投稿なら月 $0.18 で、無料枠がなくても実質的な負担はほぼゼロだと分かった。そこで「無料枠の中でやる」ではなく「月額上限 $3 を決めて、その中でやる」という制約に置き換えた。

学び: 外部サービスの料金体系は、記憶や過去の知識ではなく毎回公式ドキュメントで参照日つきで確認する。特にX APIは2023年以降、料金改定を繰り返している。「無料枠がある」という前提で設計を進めると、崩れたときに構造ごとやり直しになる。最初から「上限額を決める」形の制約にしておけば、料金体系が変わっても設計は生き残る。

課題 2思わぬ好都合

コスト最適化と、リーチ最適化が、たまたま同じ方向を向いていた

何が起きたか: URL付き投稿はAPI単価が13倍（$0.015 → $0.20）と分かり、コストを抑えるならリンクを本文に入れたくない。一方で別の調査から、X は本文内リンク付き投稿の初速リーチを30〜50%落とすため、リンクは返信欄に置くのがそもそも定石だと判明した。

どう解決したか: 「リンクは本文に入れず返信欄に置く」という1つのルールで、コストとリーチの両方が最適になる。迷う余地がなくなった。

学び: 制約（お金）と目的（リーチ）が衝突すると思い込んで妥協案を探し始める前に、両方の理由を並べてみると、同じ結論に収束していることがある。調査を分担して並列で走らせたからこそ、無関係に見えた2つの発見が突き合わせられた。

課題 3アーキテクチャ

「承認ボタンを押すだけ」を実現しようとすると、常駐サーバが必要になってしまう

何が起きたか: 「ユーザーは判断のみ」を実現するには、Discordの通知にそのまま承認ボタンを付けるのが最も手数が少ない。ところが調べると、(1) 通常のIncoming Webhookで送ったボタンはエラーも出ないまま表示されない、(2) ボタンのクリックを受け取るには公開HTTPSのエンドポイントが要る、という二重の壁があった。常駐サーバを持つとVPS費用と運用負荷が発生し、「負担を減らす」という目的と矛盾する。

どう解決したか: 役割を分けた。Discordは「通知＋リンクを1タップで開く」までに徹し、実際の承認操作はNotionページ上のボタンプロパティで行う。 エージェントは次回のcron実行時にステータスの変化を検知して後続処理を走らせる。これで常駐サーバがゼロのまま、ユーザーの操作は「通知をタップ → ボタンを押す」の2アクションに収まった。

学び: 「即時に反応する」ことと「常駐しない」ことはトレードオフに見えるが、通知の即時性と処理の即時性を分ければ両立する。人間が判断するまでの時間の方が、cronの待ち時間よりずっと長い。エラーも出ずに機能が無効化される仕様（Discordのボタン、Claudeのプロンプトキャッシュの最小トークン数）は特に危険で、実装前に必ず確認しておく価値がある。

課題 4エビデンス

「日本の個人開発者がSNS発信で受託案件を獲得した」定量的な一次事例が、ほとんど存在しなかった

何が起きたか: X・note・YouTube・Qiita/Zenn・Instagram/Threads・Facebookと、6つの媒体それぞれに調査を割り当てたが、どの媒体でも「投稿→受注」を数字で裏付ける一次情報は見つからなかった。 出てくるのは定性的な体験談か、営業目的で書かれた二次情報ばかりだった。

なぜ困ったか: 「この媒体をやれば何件取れる」という見積もりの根拠が作れない。当てずっぽうの数字を書けば、それを信じて時間を投じることになる。

どう解決したか: エビデンスがないこと自体を発見として扱い、戦略書に明記した。そのうえで、期待値を控えめに置き（90日で商談1〜3件・受注0〜1件）、「成果が出る前にやめること」を最大のリスクとして扱う設計に切り替えた。だからこそ運用負荷を週30分に抑えることが、戦略の飾りではなく本体になった。

学び: 調査で「見つからなかった」ことを、探し方が悪かったせいにして無理に何かを書かない。「エビデンスがない」は立派な調査結果であり、それを前提にすると戦略の重心が「成果の最大化」から「継続可能性の確保」へ正しく移る。なお、成功者が事例を公開しないだけの可能性もあるので、「効果がない」と断定はしていない。

課題 5法令・規約

「DMを自動送信する」という当初のイメージが、ほぼ全面的に規約違反だった

何が起きたか: 見込み客へのDM送信を自動化したかったが、調査するとX・Instagram・LinkedIn・Facebookのすべてで、同意なき自動DM送信と自動化ツールの使用が明確に禁止されていた。LinkedInは2026年に検知が厳格化し、警告なしの即時停止事例が確認されている。日本の特定電子メール法も、原則としてオプトインを求めている。

どう解決したか: 自動化の境界を引き直した。

  • 送信先を変えた: SNSのDMではなく、企業がサイトに公開している問い合わせ窓口・公表メールアドレスへ送る。特定電子メール法には「自己の電子メールアドレスを公表している団体・営業を営む個人」はオプトイン規制の対象外という例外があり、ここに乗る。オプトアウト導線と送信者情報は必ず明記する
  • 自動化の範囲を変えた: リスト生成・スコアリング・文面生成までを自動化し、送信は人間が行う。SNSのDMを使う場合も下書きまで
  • リスト作成元を変えた: SNSのスクレイピングをやめ、法人番号Web-API・gBizINFO・補助金採択事業者一覧という公開・無料・規約上クリーンな公的データに切り替えた

学び: 「やりたいこと」を規約が禁じているとき、諦めるか強行するかの二択ではない。「送信先」「自動化の範囲」「データの出どころ」のどれかを変えれば、目的は保ったまま合法な経路が見つかることが多い。 むしろ公的データに切り替えたことで、補助金の採択歴という「予算と投資意欲が実証済み」の強力なスコアリング特徴量が手に入り、リストの質はSNSから拾うより上がった。制約が設計を良くした例。

課題 6スコープ管理

「露出メディアは増やしてよい」を素直に受けると、運用負荷が青天井になる

何が起きたか: 媒体を増やすほど接点は増えるが、そのまま作ると「媒体数 × 承認回数」で作業が増える。同一文の使い回しはアルゴリズムに抑制されるため、コピペで済ませることもできない。

どう解決したか: 承認の単位を投稿ではなくハブ記事1本に固定した。人間が中身を判断するのは週1回のハブ記事だけで、そこから生成される媒体別の投稿は「リスク低」として一括承認の対象にする。媒体が1つ増えても、増えるのは一括承認の画面に並ぶカードが1枚だけ。

実装面では Postiz と Mixpost の設計を参照し、媒体差分をコードのif分岐ではなく capabilities という設定データに寄せた。「新規媒体の追加がアダプタ1クラス＋設定追加で完結しない場合は設計違反として差し戻す」を受入基準（NFR-2）に明記した。

学び: 「負荷を逓増させない」は心がけではなく受入基準として書けなければ守れない。判断の単位を作業の単位から切り離す（＝1回の判断が複数の作業を確定させる）のが、人間の負荷を一定に保つ一般解になりそう。

課題 7品質

LLMに営業文を全文生成させると、コピペ感と事実誤認の両方を招く

何が起きたか: パーソナライズすると返信率が約2倍という数字がある一方、テンプレートに名前を差し込むだけでは効果が薄い。かといって全文をLLMに書かせると、存在しない実績や誇張表現が混ざるリスクが上がる。

どう解決したか: 可変域を「冒頭の1〜2文」だけに絞った。 手順は、①公開情報から出典URL付きのファクトシートを構造化データとして抽出 → ②そこから個別化に使える一文の候補を生成（出典が紐付かない候補は破棄）→ ③定型テンプレートに1文だけ差し込む。加えて品質ゲート（出典なし・数値不一致・禁止語・過去文面との類似度超過を自動で弾く）を通す。判定の一次はルールベース＋Haikuの二段で、最終承認は必ず人間。

学び: 生成AIの品質は、モデルやプロンプトの巧拙より「生成させる範囲をどれだけ狭くできるか」で決まる部分が大きい。出力トークンが減るのでコストも下がり、レビューも速くなる。ハルシネーション対策として最も効いたのは「出典URLが紐付かない生成物は無条件で破棄する」という単純な機械的ルールだった。

課題 8プロセス

28体の並列エージェントは、そのままでは「重複した一般論」を大量に返してくる

何が起きたか: 100体並列という当初の希望に対し、トークンコストとの兼ね合いで30体規模に調整した。それでも調査軸の切り方が甘いと、複数のエージェントが同じ一般論を返して統合の手間だけが増える。

どう解決したか: 各エージェントへの指示に4つの制約を入れた。①出力を500〜700語に制限、②【事実と出典URL】【示唆】【実装への落とし込み】という構造を固定、③検索回数の上限を明示、④「不確かな内容は推測と明記」を必須にした。特に④が効いた。推測と事実が分離されて返ってくるので、統合時に「これは根拠がある」「これは推測だ」を判断するコストがほぼゼロになり、戦略書にもその区別をそのまま持ち込めた。

学び: 並列調査の価値は「量」ではなく「軸の重ならなさ」で決まる。同じ問いを100人に聞いても同じ答えが100回返るだけ。そして出力フォーマットを固定することが、統合コストを下げる最大の投資だった。次回も同じ4制約を使う。

課題 9戦略の出発点

手持ちの資産から市場を選んでいた（最も重い間違い）

何が起きたか: 初版では「既存の35本に店舗運営系（HACCP点検・シフト・在庫予測・SOP生成）が4本あるから、店舗運営DXを看板にする」と決めていた。一見もっともらしいが、これは需要ではなく在庫から市場を選んでいる。指摘を受けて需要側から選び直した結果、結論はまったく別の場所に着地した。

調べ直して分かったこと:

  • 建設・不動産は既に埋まっていた。 建設はANDPADが21万社・55万人、不動産はいえらぶCLOUDが4.4万社。需要が大きい業界ほど、既に業界標準が決まっている
  • 税理士事務所は痛みが大きいのに参入が遅かった。 確定申告期の残業は閑散期の2.4倍で明らかな痛みがあるが、freeeが2026年7月に資料回収機能、8月にAIエージェント版を投入済み。痛みが分かりやすい市場は、大手も同じことに気づいている
  • コストの壁が制度的に外れている分野が1つだけあった。 中小企業のIT投資の最大の障壁はコスト負担だが、介護テクノロジー導入支援事業は補助率が最大3/4〜4/5。200万円の案件が実質40〜50万円になり、経営者が単独決裁できる金額帯に収まる
  • 市場が求めているのは「作る人」ではなかった。 失注理由の上位は「旗振り役がいない」31.0%、「使いこなせない」26.4%、「効果が分からない」22.1%と、技術ではなく人と運用に集中していた。だからオファーに導入・定着の伴走を含めることにした

学び: 「自分は何を作れるか」から始めると、作れるものの中で一番マシな市場にしか辿り着けない。「誰が、いま、金を払ってでも解決したがっているか」から始めると、候補そのものが入れ替わる。今回、最も強い決め手になったのは技術でも痛みの大きさでもなく、「補助金でコストの壁が外れている」という制度的な条件だった。これは自分の技術の棚卸しからは絶対に出てこない。

もう1つ。「痛みが大きい市場」と「勝てる市場」は違う。 痛みが大きく分かりやすい市場（税理士の確定申告期、建設の書類）は、既に大手が入っている。個人が狙うべきは「痛みはあるが、大手の経済合理性が及ばない場所」— 今回なら既存介護ソフトの周辺、社労士という規模の小さい市場だった。

課題 10意思決定

推奨を出すために、まだ確かめていない前提が1つ残っている

何が起きたか: 介護・障害福祉を第1ターゲットに推す最大の根拠は「補助率3/4〜4/5」だが、補助対象になるには製品が自治体の認定リストに載っている必要がある可能性が高い（推測。今回の調査では確認できなかった）。もし個人事業者が登録できない、既製品しか対象にならないのであれば、この根拠は丸ごと崩れる。

どう扱ったか: 曖昧なまま推奨を出すことも、確認できるまで結論を保留することもしなかった。推奨は出したうえで、それが崩れる条件と、崩れた場合の代替（社労士事務所への繰り上げ）を並べて書いた。 そして90日ロードマップのDay1の最初の項目を「補助金の適用可否を確認する」にした。

学び: 戦略の結論が1つの前提に強く依存しているとき、その前提を隠して滑らかな結論を書くと、後で崩れたときに何をやり直せばいいか分からなくなる。「この判断はここに乗っている」と明示し、確認手順と代替案をセットで置くほうが、読み手が自分で判断を更新できる。1回の調査で分からなかったことは、電話1本で分かることが多い。

次フェーズ（実装）に持ち越す注意点

#注意点理由
1プロンプトキャッシュは tools → system → messages の順序を厳守し、可変値（日時・対象企業名）を必ず最後尾に置く途中の1バイトの変更で以降のキャッシュが全て無効化される。しかもエラーは出ない。usage.cache_read_input_tokens を必ずログに出して監視する
2Haiku 4.5 の最小キャッシュ長は4,096トークンSonnet（1,024）やOpus 5（512）の感覚で組むと、Haikuだけ黙ってキャッシュが効かない
3Batch APIは最大24時間で失効する（失効分は課金されない）週次バッチなら問題ないが、日次の返信トリアージには使わない
4スケジューラはAPSchedulerではなくGitHub Actionsに寄せるモジュールレベルでAPSchedulerを起動するプロジェクトを hub_app.py に登録すると多重起動する（既知の問題）。Actions側に寄せれば常駐プロセスもVPS費用も不要になる
5成果物を毎回リポジトリにコミットする設計にする60日間活動がないとGitHub Actionsのscheduleが自動停止する。ログのコミットがそのまま停止防止になる
6X APIの支出上限は開発者ポータル側にも設定する環境変数側のガードだけではバグで突破されうる。従量課金は上限を外部にも置く
7承認1件あたりの判断時間を実測するNFR-1（週30分以内）を満たせないなら、それは意志の問題ではなく承認画面の情報設計の問題。Notion運用から自前UIへの移行を判断する材料にする

このフェーズの総括

最も価値があった判断は、市場を「自分が作れるもの」ではなく「需要」から選び直したこと。次いで「無料枠でやる」を「上限額を決めてやる」に、「DMを自動送信する」を「送信先とデータの出どころを変える」に置き換えたこと。3つとも共通して、当初の前提が使えないと分かったときに、目的を保ったまま手段だけを差し替えている。

逆に最も危なかったのは、日本語圏の成功事例が見つからないまま「たぶん効くだろう」で数字を書きそうになったこと。エビデンスの不在を正直に書いたことで、戦略の重心が「成果の最大化」から「続けられること」へ移り、結果として週30分という設計制約が生まれた。
