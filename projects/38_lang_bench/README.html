README — バックエンド言語 性能比較ベンチマーク

導入から計測、レポート閲覧までの手順書。仕様の背景は 要件定義.html、開発上の課題と解決策は 振り返り.html を参照。

これは何か

8言語（Python / Go / Ruby / TypeScript / Java / C# / PHP / Rust）に完全に同一の業務処理を実装し、同一のCPU・メモリ上限を課したDockerコンテナ上で、同一の負荷を流して性能を比較する計測基盤。処理完了時間・スループット・応答時間の裾・CPU/メモリ消費を並べて出す。

全言語を同時に走らせる同時実行モードを備え、共通の壁時計時刻（スタートバリア）で一斉にスタートさせることで、リソース競合下での劣化の仕方も測れる。

1.3 ホストに言語処理系は要るか

計測だけなら不要。 8言語すべてコンテナ内でビルドされる。

ただし make test（ロジック一致テストとHTTP層の検査）はホストの処理系を使うため、フルで走らせるには go / ruby / npm / mvn / php / cargo / dotnet が必要になる。揃っていないのが普通なので、ローカルでは make test-quick（入っている言語だけ検証し、欠けている言語を明示的に報告する）を使い、8言語すべての検証は CI に任せる。

実行場所に関する注意

計測はPC実機または専用VPSでのみ行うこと。クラウド開発セッションはCPU割当が共有かつ変動し、そこで出した数値は再現性がないため言語選定の根拠にできない。

1.4 Windows での実行

Windows ネイティブ（PowerShell / コマンドプロンプト）では動かない

本プロジェクトのコマンドは Linux/macOS シェル前提で、Windows では以下が引っかかる。WSL2 上で実行すること。

箇所Windows ネイティブでの問題
make標準で入っていない
nproc存在しない（echo %NUMBER_OF_PROCESSORS% が相当）
BENCH_CPUS=1.0 make bench環境変数の前置きは POSIX シェル構文。PowerShell では $env:BENCH_CPUS="1.0"
python3通常は python
Makefile 内の grep / awk / read -pUnix ツール前提

計測の妥当性は WSL2 でも変わらない。 計測対象は Linux コンテナであり、Docker Desktop はもともと WSL2 をバックエンドに使っているため、ネイティブ実行と同じコンテナが同じように走る。

WSL2 での手順

# 1) WSL2 の確認（未導入なら PowerShell を管理者で開いて wsl --install）
wsl -l -v

# 2) Docker Desktop の設定
#    Settings → Resources → WSL Integration で使用するディストリビューションを有効にする

# 3) WSL のシェルに入り、必要なら make を入れる
wsl
sudo apt-get update && sudo apt-get install -y make

# 4) 以降は本書の手順どおり
cd /mnt/c/<リポジトリを置いた場所>/portfolio/projects/38_lang_bench
make test-quick

リポジトリの置き場所に注意

/mnt/c/...（Windows 側のディスク）に置くとファイルI/Oが遅く、ビルド時間が大きく伸びる。可能なら WSL のホームディレクトリ配下（~/portfolio）にクローンするほうが速い。ただし計測されるのはコンテナ内のCPU処理なので、ビルドが遅いだけで計測値そのものは変わらない。

make を使わない場合

make が使えない環境では、Makefile の各ターゲットの中身をそのまま打てばよい。

python3 harness/run_tests.py                      # make test-quick 相当
docker compose build                              # make build 相当
docker compose --profile tools up -d py go rb ts java cs php rs console   # make console 相当
python3 harness/verify_parity.py                  # make verify 相当
python3 harness/bench.py --mode both              # make bench 相当
docker compose --profile tools down --remove-orphans   # make down 相当

3. 動作確認

3.1 CLI での確認

make up          # 8サービスを起動
make verify      # 8実装が同じ計算結果を返すか検証

make verify は8サービスに同一リクエストを投げ、lang フィールドを除く応答が完全一致するかを確認する。ここが通らない状態で性能を測っても意味がないので、先に原因を潰すこと。

3.2 ブラウザからの実行テスト

make console     # 8サービス + コンソール(nginx) を起動

ブラウザで http://localhost:18080 を開き、上から順に実行する。

ボタン確認できること
1. ヘルスチェック8サービスが起動し応答しているか
2. パリティ検証8実装が同じ金額・同じ署名を返すか（Python基準で比較）
3. 簡易スループット測定並列度1での逐次応答時間の傾向。絶対値は本計測と一致しない

コンソールは nginx リバースプロキシ経由で8サービスを同一オリジン配下に置いている。本計測時には起動しない（Compose の profiles: ["tools"] で分離済み）。

3.3 単発リクエストで確認する場合

curl -s -X POST http://localhost:18002/api/v1/score \
  -H 'Content-Type: application/json' \
  -d '{"order_id":"ORD-1","items":[{"sku":"SKU-1","qty":2,"unit_price":1500.5}],
       "customer":{"tier":"gold","history_days":400},"rounds":200}'

ポートを 18001〜18008 のどれに変えても、lang 以外は同じ応答が返るはず。

4. 計測の実行

4.1 まず短縮版で通す

make down    # 動作確認で起動したコンテナを止める
make quick   # 約5分。全工程が通ることの確認用

4.2 本計測

make bench   # 8言語で約20分。isolated（単独）と concurrent（全言語同時）の両方

# ホストが小さい場合は言語を絞る
python3 harness/bench.py --mode both --langs go rs java py

実行の流れ:

  1. 前提チェック（docker / compose / デーモン接続）
  2. イメージビルド、k6 イメージ取得
  3. isolated: 1言語ずつ単独起動 → healthz 待ち → 3秒安定待ち → 資源サンプラ起動 → 負荷実行 → 停止。これを言語数ぶん繰り返す。
  4. concurrent: 全言語同時起動 → healthz 待ち → スタートバリア時刻を確定 → 全ての k6 を起動 → 一斉スタート → 全終了待ち
  5. 生データを results/<日時>/ に保存し、report.html を生成

4.3 パラメータを変えて測る

# CPU寄りの負荷（署名の反復を10倍に）
python3 harness/bench.py --mode both --rounds 2000

# JSON/メモリ寄りの負荷（明細を10倍に）
python3 harness/bench.py --mode both --items 120

# 高並行（同時接続数を4倍に）
python3 harness/bench.py --mode both --vus 200

# 同時実行だけ／長めに
python3 harness/bench.py --mode concurrent --steady 180s
オプション意味既定
--modeisolated / concurrent / bothboth
--langs対象言語（py go rb ts java cs php rs から選ぶ）全8言語
--vus定常負荷の同時接続数50
--rounds1リクエストあたりのSHA-256反復数（CPU比重）200
--items1注文あたりの明細数（JSON/メモリ比重）12
--warmup / --steady各フェーズの長さ15s / 60s
--barrier同時実行のスタートバリアまでの猶予秒。言語を増やすほど長くする15.0
--skip-buildビルドを飛ばす（2回目以降）—

コンテナのリソース上限は環境変数で変えられる。全言語で必ず同じ値にすること。compose の共通アンカーで一括適用されるため、通常は個別に触る必要はない。

BENCH_CPUS=4.0 BENCH_MEMORY=1g BENCH_WORKERS=4 make bench

Java（Spring Boot）と C#（ASP.NET Core）は常駐メモリが大きい。既定の 512MB で起動に失敗する場合は BENCH_MEMORY を上げて全言語で同じ値にしてから測り直すこと。片方だけ上げると比較が成立しない。

5. 結果の見方

計測が終わると results/<日時>/report.html が生成される。ブラウザで開く。

指標読み方
スループット RPS同じ同時接続数で捌けた秒間リクエスト数。高いほど良い。処理1件あたりの所要時間の逆数に近い。
p50 / p95 / 最大 (ms)応答時間。平均より p95 と最大が重要。商用SLAは平均ではなく裾で切られる。
失敗率定常時に1%を超えるなら、その言語はその負荷に耐えていない。
スパイク p95定常 p95 から大きく跳ねる言語は突発トラフィックに弱い。
CPU平均上位50%サンプルの平均（アイドル区間を除外）。同じRPSならCPUが低いほうがサーバ単価が安い。
メモリ最大コンテナのピークRSS。上限512MBに張り付いていないかを確認する。

単独と同時、両方を見る

同時実行の数値は単独より必ず悪くなる。見るべきはその劣化幅で、幅が小さい言語ほど1台のホストに複数サービスを同居させる構成に向く。単独の絶対値だけでは本番の挙動は分からない。

生データ

ファイル内容
manifest.json実行パラメータ、ホスト情報、壁時計時間
k6-{py,go,rb}.json単独実行のレイテンシ・スループット全指標
concurrent/k6-*.json同時実行時の同上
resource-*.csv1秒刻みのCPU・メモリ・ネットワーク時系列

results/ は .gitignore 済み。共有したい結果は report.html を個別に取り出すこと。

レポートだけ作り直したい場合: make report（最新の結果ディレクトリを対象にする）。特定の結果を指定する場合は python3 harness/report.py results/20260902-100000。

6. 計測の信頼性を保つために

  1. 計測前に他の重い処理を止める。 ブラウザの重いタブ、他のコンテナ、バックアップ処理など。
  2. 同条件で最低3回走らせる。 1回の結果で判断しない。ばらつきの幅を見てから結論を出す。
  3. 条件の違う結果を並べない。 manifest.json のパラメータとホスト論理CPU数が一致する結果同士だけを比較する。
  4. コードを触ったら make test（または make test-quick + CI）。 実装のロジックがずれた状態の計測は無意味。
  5. ノートPCは電源接続で。 バッテリー駆動だとCPU周波数が絞られ、実行のたびに条件が変わる。

7. トラブルシューティング

症状原因と対処
[FATAL] docker デーモンに接続できないDocker Desktop / dockerd が起動していない。起動してから再実行する。
[FATAL] 起動待ちタイムアウトサービスが healthy にならない。docker compose logs py go rb で原因を確認する。ビルド失敗やポート競合が多い。
ポートが使用中というエラー18001〜18003 / 18080 が他プロセスに取られている。docker-compose.yml の ports を変更する。
k6 の終了コードが 99異常ではなく閾値未達。その言語がその負荷条件で受け入れ基準を満たさなかったということ。結果は正常に記録されている。
全言語の RPS が不自然に近い負荷元（k6）が飽和している可能性。--vus を下げるか、負荷元を別ホストに出す。
レポートの値が n/a だらけloadgen/scenario.js の thresholds からサブメトリクスの宣言が消えている。宣言したタグ付きメトリクスしか集計に現れない。
make test でどれかの言語が落ちる実装のロジックがずれている。仕様を変えたなら make golden で期待値を再生成し、8実装すべてを直す。
make test が途中で止まるその言語のツールチェーンがホストに無い。make test-quick を使う（欠けている言語を報告して続行する）。
CI が「golden.json が古い」で落ちるservices/python/core.py を変えたのに期待値を再生成していない。make golden を実行してコミットする。
Java / C# コンテナが起動しないメモリ上限が足りない可能性が高い。docker compose logs java cs を確認し、BENCH_MEMORY を全言語で引き上げる。
concurrent モードで一部の言語だけ結果が欠けるコンテナ起動がスタートバリアに間に合っていない。--barrier を伸ばす。
Rust / Ruby のビルドが遅いRust は LTO 有効の release ビルド、Ruby はネイティブ拡張のコンパイルによるもの。いずれも初回のみ。

8. 片付け

make down                    # コンテナを停止・削除
docker compose down --rmi local   # イメージも削除する場合

make clean は results/ 配下の計測結果を削除する。実行前に必要な結果を退避したか確認すること（確認プロンプトが出る）。

9. CI（GitHub Actions）

.github/workflows/lang-bench.yml が、このプロジェクトに触る PR で自動的に走る。

ジョブ / ステップ検証内容
期待値ファイルの鮮度gen_golden.py を再実行し tests/golden.json に差分が出ないこと。Python 実装を変えて再生成し忘れると、他言語だけが古い期待値と比較され続けるため。
全8言語のロジック一致8つのツールチェーンを用意して run_tests.py を実行。SKIP が1つでも出たら失敗させる（見逃すとその言語だけ未検証のまま緑になる）。
HTTP層のビルド/構文検査ロジックテストは core しか読まない。Go / TypeScript / Java / Rust はテストがHTTP層まで巻き込んでコンパイルするが、Python / Ruby / PHP / C# は core しか通らない。この4つを別途検査し、実機ビルドで初めて落ちるのを防ぐ。
Compose 定義の検証docker compose config が通ること。
リソース上限の均一性全サービスの cpus / mem_limit が完全一致すること。公平性の根幹なので目視に頼らない。

ローカルに8言語すべてのツールチェーンが揃っていることは稀なので、全言語での検証はこの CI が唯一の場になる。手元では make test-quick で回し、最終的な担保は CI の緑で確認する。
