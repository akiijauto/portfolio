振り返り — Python / Go / Ruby 性能比較ベンチマーク

開発中に実際にぶつかった課題と、その解決策。次に同種のベンチマークを作るときに繰り返さないための記録。
作成日: 2026-09-02 ／ 対象: portfolio/projects/38_lang_bench

総括

このプロジェクトで一番時間を使ったのは、3言語のコードを書くことではなく「3つが本当に同じ仕事をしていると証明すること」と「計測が言語以外の要因で汚れないようにすること」だった。ベンチマークの価値は数値の精度ではなく、その数値が何を比べているかを説明できるかどうかにある。

課題と解決策

1. Python の round() が偶数丸めで、3言語の金額が食い違った正確性

起きたこと
同一の注文データに対し、Python だけが Go / Ruby と異なる合計金額を返した。round(2.675, 2) が Python では 2.67、Go の math.Round と Ruby の Float#round では 2.68 になる。
原因
Python の組み込み round() は「0.5 を偶数側へ」丸めるバンカーズ丸め。Go / Ruby は「0.5 を絶対値の大きい側へ」丸める。言語の標準関数の名前が同じでも意味が同じとは限らない。
対処
Python 側で明示的に math.floor(x*100+0.5)/100 を実装し、丸め方を仕様として固定した。加えて「Python の round は偶数丸めなので使えない」という理由をコード内コメントとテストの両方に残した。 
def round2(value: float) -> float:
    """Go の math.Round / Ruby の Float#round と同じ「0.5は絶対値の大きい側へ」。
    組み込みの round() は偶数丸めなので、そのまま使うと3実装で金額が食い違う。"""
    if value >= 0:
        return math.floor(value * 100 + 0.5) / 100
    return -(math.floor(-value * 100 + 0.5) / 100)

学び: 複数言語で同一ロジックを実装するときは、丸め・ソートの安定性・辞書の順序・整数除算の符号といった「暗黙の仕様」が最初に破綻する。処理の流れではなく境界値から先にテストを書く。

2. 「3実装が同じ仕事をしている」保証が無いまま計測しかけた設計

起きたこと
当初は計算ロジックを各言語の HTTP ハンドラの中に直接書いていた。この状態では、実装差を検出するには実際にサーバを3本起動して叩くしかなく、Docker が使えない環境では検証できなかった。
なぜ問題か
性能比較は「同じ仕事をさせている」ことが唯一の前提。片方が手を抜いていれば速いのは当たり前で、数値は無意味になる。この前提の検証コストが高いと、忙しいときに検証が省かれて壊れた比較が残る。
対処
計算ロジックを HTTP 層から切り離した（core.py / score.go / core.rb）。Python 実装を基準として期待値を tests/golden.json に固定し、Go と Ruby のテストが同じファイルを読んで完全一致を検証する構成にした。Docker もサーバ起動も不要で、数秒で3言語の一致が確認できる。署名（SHA-256 の200回チェーン）まで含めて一致することを機械的に保証している。

学び: ベンチマークにおける「同一性の検証」は付随的なテストではなく主要機能。検証を安く速くする設計に投資すると、以後すべての計測結果の信頼性が上がる。

3. k6 のフェーズ別集計ができず、ウォームアップの遅さが本計測に混ざった計測

起きたこと
ウォームアップ・定常・スパイクの3フェーズを1つのシナリオで走らせたところ、サマリが全フェーズ合算の数値しか出さなかった。ウォームアップ中の遅いリクエストが p95 を押し上げ、特に JIT を持つ Ruby が不当に不利になった。
原因
k6 はタグ付きサブメトリクスを自動では集計しない。thresholds に書いたサブメトリクスだけが サマリの data.metrics に現れる、という仕様を把握していなかった。
対処
フェーズ別に見たい指標をすべて thresholds に宣言し、handleSummary() で JSON に書き出すようにした。閾値が「受け入れ基準」と「サブメトリクスの宣言」を兼ねている点をコメントで明記し、うっかり消すとレポートが空になることを警告した。 
// thresholds は受け入れ基準であると同時に「サブメトリクスの宣言」でもある。
// ここに書いたタグ付きメトリクスだけが handleSummary の data.metrics に現れる。
thresholds: {
  'http_req_duration{phase:steady}': ['p(95)<1000'],
  'http_reqs{phase:steady}':         ['count>0'],
  ...
}

学び: 計測ツールは「取得したデータ」と「出力するデータ」が一致しない。欲しい数値がレポートに出るところまでを最初に一度通すべきで、負荷シナリオを作り込んでから集計方法を考えると作り直しになる。

4. 負荷をホストの公開ポート経由でかけ、docker-proxy がボトルネックになった計測

起きたこと
初期案では http://localhost:18001 のようにホスト公開ポートへ負荷をかける想定だった。この経路では全トラフィックが docker-proxy を通り、高負荷時にはそこが詰まって3言語とも似たような数値に収束してしまう。
対処
負荷生成コンテナを計測対象と同じ Docker ネットワークに参加させ、http://bench-go:8000 のようにコンテナ名で直接叩く構成にした。ホスト公開ポートは動作確認とブラウザテスト専用と位置づけた。

学び: 差が出ないときは「差が無い」ではなく「経路上の別の何かで頭打ちになっている」を先に疑う。計測対象より手前に共通のボトルネックがあると、あらゆる比較が潰れる。

5. 3言語同時実行の開始タイミングがずれ、先に始まった言語が有利になった公平性

起きたこと
3本の負荷コンテナを順に docker run -d で起動すると、コンテナ生成とスクリプト読み込みに数秒のばらつきが出る。最初に始まった言語は空いている CPU を独占でき、最後の言語は最初から競合状態で走ることになる。これでは同時実行を測る意味がない。
対処
スタートバリアを実装した。オーケストレータが「現在時刻 + 8秒」を epoch ミリ秒で確定し、3本すべてに同じ値を START_AT として渡す。各負荷スクリプトは setup() でその時刻まで待ってから走り出す。ユーザ要望の「3つの Docker を同時に動かすタイマー」はこの仕組みで実現している。
実装上の注意
k6 の sleep() は秒単位なので、ミリ秒精度を出すためにビジーウェイトにした。待機は負荷開始前なので計測値には影響しない。

学び: 「同時に動かす」は「同時に起動コマンドを打つ」ではない。比較したい条件を揃えるには、揃えるための仕掛けを明示的に作る必要がある。

6. 監視スタックを入れようとして、観測が観測対象を歪めることに気づいた計測

起きたこと
資源使用量の計測に cAdvisor + Prometheus + Grafana を立てる案を検討した。時系列の精度は高いが、監視スタック自身が同じホストの CPU を数十%消費する。3コンテナで CPU を奪い合う状況を測りたいのに、観測装置が第4の競合者として混ざる。
対処
docker stats を1秒間隔でポーリングして CSV に落とすだけの薄いサンプラに切り替えた。精度は落ちるが観測コストが最小で、比較の公平性を壊さない。この判断理由を collector.py の冒頭コメントに残し、「精度が必要になったら差し替える」ことを明記した。

学び: 計測系の道具選びは「精度が高いほど良い」ではない。観測が対象に与える影響を勘定に入れて、目的に対して十分な最小の手段を選ぶ。

7. ブラウザ実行テストの CORS を、計測対象サーバに手を入れずに解決した設計

起きたこと
ブラウザから3サービスを叩くテスト画面を作ろうとしたが、ポートが違うため CORS で弾かれる。素直に対処するなら3サービスすべてに CORS ヘッダ処理と OPTIONS ハンドラを足すことになる。
なぜ問題か
計測対象のハンドラにベンチマーク本来の仕様に無い処理を足すことになる。3言語それぞれで実装コストが違うため、その差がそのまま性能差として混入する。
対処
nginx のリバースプロキシを1本立て、3サービスを /api/py/ /api/go/ /api/rb/ として同一オリジン配下にぶら下げた。CORS 自体が不要になる。さらに Compose の profiles: ["tools"] でこのコンテナを分離し、本計測時には起動しないようにした（nginx が CPU を分け合うと比較が歪むため）。

学び: 計測対象に手を入れずに済ませる方法を先に探す。「テストのために本体を変える」は最後の手段で、特にベンチマークでは変更そのものが結果を汚す。

8. CPU 使用率の平均が、アイドル区間に薄められて実態を表さなかった計測

起きたこと
資源サンプラは起動待ち・安定待ち・負荷終了後もサンプルを取り続けるため、単純平均を出すとアイドル区間（CPU 数%）に引っ張られ、負荷中の実際の消費が読めなくなった。
対処
CPU 使用率のサンプルを降順に並べ、上位50%だけを平均する方式にした。負荷区間はサンプル全体のおおむね半分以上を占めるため、アイドル区間を機械的に除外できる。この処理の意図をコードコメントとレポート本文の両方に書き、読み手が「単純平均ではない」ことを誤解しないようにした。

学び: 集計方法は数値と同じくらい重要な情報。加工したなら、加工したことをレポートの読み手に伝える。伝えない集計は誤読を生む。

9. クラウドセッションに Docker デーモンが無く、実測ができなかった環境

起きたこと
開発を行ったクラウドセッションには docker コマンドはあるがデーモンが動いておらず、コンテナのビルドも起動もできなかった。Python の FastAPI も Ruby の Sinatra も未導入で、サーバを直接起動しての確認もできない。
対処
検証を2層に分けた。Docker を必要としない層（3言語の計算ロジックの一致）を切り出し、その環境で実際に走らせて Go・Ruby・Python すべてで期待値との完全一致を確認した。Docker を必要とする層（性能計測そのもの）は PC 実機の作業と明示的に位置づけ、要件定義と README の両方に実行場所の分離表を書いた。
結果
クラウド側で保証できたこと: 3言語の全構文、計算ロジックの完全一致（署名・丸め・ソート順を含む）、バリデーション挙動、レポート生成器の動作（合成データで検証）。
PC 実機に残したこと: イメージビルド、負荷計測、ブラウザ実行テスト。

学び: 環境の制約は「できない」で止めず、できる検証とできない検証に分解する。分解できれば、制約のある環境でも品質の大半は先に確保できる。そして「どこまで検証済みか」を文書に残しておけば、実機作業者は残りだけに集中できる。

設計判断の記録（採用しなかった案とその理由）

検討した案不採用の理由
各言語で最速のライブラリ構成にする（orjson、Cアクセラレータ等）「その言語で普通に商用APIを書いたらどうなるか」を知りたいため。最速構成の比較は別の問いであり、混ぜると結論が曖昧になる。
Python 側で pydantic の自動バリデーションを使うGo / Ruby は手動でJSONを解釈しており、Python だけフレームワーク機能を使うと処理内容が変わる。公平性のため3言語とも手動解釈に統一した。
PostgreSQL を挟んで I/O 集約の負荷も同時に測るDB がボトルネックになると3言語とも同じ数値に収束し、言語差が見えなくなる。まず CPU + JSON + 並行処理の比較を確定させてから、別シナリオとして追加する。
k6 ではなく各言語で負荷生成スクリプトを書く負荷生成側の性能差が計測に混入する。負荷元は3言語すべてに対して同一でなければならない。
cAdvisor + Prometheus + Grafana で資源監視監視スタック自身が CPU を消費し、比較を歪める（課題6）。
計測結果をリポジトリにコミットする実行環境ごとに変わる生成物であり、条件の違う結果が混在すると誤った比較を生む。.gitignore し、共有はレポート単体で行う。
