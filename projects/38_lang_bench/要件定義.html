要件定義 — バックエンド言語 性能比較ベンチマーク

プロジェクト: portfolio/projects/38_lang_bench ／ 仕様ID: SPEC-API-v1 ／ 作成日: 2026-09-02

1. 背景と目的

商用サービスのバックエンド言語を選定するにあたり、「どれが速いか」という一般論ではなく、自分たちのワークロードで、自分たちのサーバ上で、どれだけの差が出るかを数値で押さえたい。

本プロジェクトは、8言語に完全に同一の業務処理を実装し、同一のリソース上限を課したDockerコンテナ上で、同一の負荷シナリオを流して比較する計測基盤である。

対象は Python / Go / Ruby / TypeScript / Java / C# / PHP / Rust。いずれも商用バックエンドで実績のある言語で、並行処理モデル（GIL、goroutine、仮想スレッド、イベントループ、プロセス分離、async/await）とメモリ管理（GC あり／なし）が意図的にばらけるよう選んである。

このベンチマークで答えたい問い

  1. 同じCPU割当で、各言語は毎秒どれだけの注文を捌けるか（スループット）
  2. 応答時間の裾（p95 / 最大）はどこまで伸びるか（SLA設計の根拠）
  3. 突発トラフィック時にどう劣化するか（スパイク耐性）
  4. 同じ処理量あたりのCPU・メモリ消費はどれだけ違うか（サーバ単価）
  5. 1台のホストに3サービスを同居させたとき、どの言語が最も崩れにくいか（集約適性）

3. 計測対象アプリケーション仕様（SPEC-API-v1）

全8実装はこの仕様に完全準拠し、同一入力に対して lang フィールドを除き1バイトも違わない応答を返さなければならない。1つでも手を抜いていれば速いのは当然で、数値の意味が失われるため。

3.1 エンドポイント

メソッド / パス役割

GET /healthz起動完了判定。Docker HEALTHCHECK とベンチ開始待ちに使う。

3.2 リクエスト / レスポンス

// リクエスト
{
  "order_id": "ORD-1000001",
  "items": [ { "sku": "SKU-0001", "qty": 3, "unit_price": 1200.55 }, ... ],
  "customer": { "tier": "gold", "history_days": 400 },
  "rounds": 200
}

// レスポンス（200）
{
  "order_id": "ORD-1000001", "lang": "go", "item_count": 3,
  "subtotal": 4016.64, "discount": 602.5, "tax": 341.41, "total": 3755.55,
  "signature": "ea47560f…", "top_skus": ["SKU-0001","SKU-0003","SKU-0002"], "rounds": 200
}

3.3 処理手順（この順序と計算式を全8言語で完全に揃える）

  1. JSONデシリアライズ — フレームワークの自動バリデーション（pydantic、Bean Validation、モデルバインド、extractor など）は使わず、全言語とも手動で解釈する。
  2. バリデーション — order_id 非空、items 非空、全明細で qty > 0 かつ unit_price ≧ 0。違反は 400 validation_failed。
  3. 金額計算 — subtotal = Σ(qty × unit_price) を小数第2位で丸める。
  4. 割引率 — gold 0.12 / silver 0.07 / その他 0.02。history_days ≧ 365 なら +0.03。上限 0.20。
  5. 税・合計 — tax = (subtotal − discount) × 0.10、total = subtotal − discount + tax。各段で丸める。
  6. 署名生成（CPU負荷の本体） — SHA-256("order_id|subtotal") を初期値に、SHA-256 を rounds 回チェーンする。
  7. 上位SKU抽出 — 明細を金額降順（同額は SKU 昇順）でソートし上位5件。
  8. JSONシリアライズして返す。

丸めに関する厳守事項

丸めは「0.5 は絶対値の大きい側へ」で統一し、全言語で floor(x*100+0.5)/100 の式に揃える。標準関数の挙動が言語ごとに違うため、名前が同じでも意味は同じではない。

言語標準の丸めそのまま使った場合
Python round()偶数丸め（バンカーズ丸め）金額が食い違う
C# Math.Round()偶数丸め（既定）金額が食い違う
JavaScript Math.round()0.5 を常に +∞ 側へ負値で食い違う
Java Math.round()0.5 を常に +∞ 側へ負値で食い違う
Go math.Round() / Ruby Float#round / PHP round() / Rust f64::round0.5 を絶対値の大きい側へ一致するが、式を揃えて仕様として固定する

3.4 負荷の可変パラメータ

パラメータ効果既定値
roundsSHA-256 の反復回数。上げるほどCPU比重が増す。200
items1注文あたりの明細数。上げるほどJSONパース／メモリ確保／GC比重が増す。12
vus同時接続数。上げるほど並行処理モデルの差が出る。50

この3つを振ることで、「CPU寄りの処理」「JSON寄りの処理」「高並行の処理」それぞれで言語の得手不得手を切り分けられる。

いずれも「その言語で商用APIを書くなら普通こうする」という構成を選んだ。最速化のためのチューニング（Cアクセラレータ、代替JSONライブラリ等）は意図的に入れていない。素の状態での比較を目的とするため。

構成選択で意図的に揃えなかった点

PHP だけは nginx + php-fpm の2段構成になっている。 他言語のようにアプリ自身がHTTPを話す構成が PHP では一般的でなく、無理に揃えると「商用のPHP」ではなくなるため。この2段構成そのものを PHP の姿として計測する。

Java と C# はフレームワーク（Spring Boot / ASP.NET Core）込みで測る。 どちらもフレームワーク無しで商用APIを書くことはまずない。起動時間とメモリ常駐量を含めた実像を見る。

4.2 公平性の担保（これを崩すと計測が無意味になる）

  • リソース上限を全8コンテナで完全に揃える。 cpus: 2.0 / mem_limit: 512m。揃えないと言語差ではなくホストの空き資源差を測ることになる。CI で機械的に検証している（下記 7.3）。
  • ワーカー並列度を揃える。 Python workers=2、Go GOMAXPROCS=2、Ruby workers=2、Node cluster=2、Rust tokio worker_threads=2。Java / C# はランタイムがコンテナのCPU上限から自動決定する。PHP は php-fpm を static 8プロセスに固定する。
  • ランタイムにコンテナ上限を認識させる。 JVM は既定でホストのメモリを見に行くため -XX:MaxRAMPercentage=75 を指定する。Rust の Tokio も available_parallelism 任せにせず環境変数で明示する。
  • ウォームアップを必ず挟む。 JIT / YJIT / コネクションプール / ページキャッシュが温まる前の数値は捨てる。
  • 負荷元はコンテナ名で直接叩く。 ホストの公開ポート経由にすると docker-proxy がボトルネックになり、言語差ではなくポートフォワードの詰まりを測ることになる。
  • ペイロードは固定シードで事前生成する。 負荷元のリクエスト生成コストが計測に混ざらないようにする。
  • ブラウザ用コンソール（nginx）は計測時に起動しない。 Compose の profiles: ["tools"] で分離する。

5. 計測設計

5.1 負荷フェーズ（1回の実行につき3段）

フェーズ内容目的
warmup（既定15秒）VU = 定常の1/5ランタイムを温める。集計対象外。
steady（既定60秒）VU 固定（既定50）本計測。言語間比較の主データ。
spike（25秒）VU を 4倍まで急増させ戻す飽和時の劣化の仕方を見る。

5.2 実行モード（2種類。両方を1回の run で回す）

モードやること読み取れること
isolated1言語ずつ単独で起動して負荷をかける。計測対象以外のコンテナは停止する。その言語の素の性能。言語選定の主データ。
concurrent全言語を同時起動し、共通の壁時計時刻（スタートバリア）で負荷を一斉に開始する。ホストCPUを奪い合う状況での劣化幅。1台に複数サービスを同居させる構成の適性。

concurrent の数値は isolated より必ず悪くなる。単独の絶対値だけを見ても本番の挙動は分からず、同時実行だけを見ても言語の素の力は分からない。両者を並べて初めて意思決定に使える。

5.3 同時実行タイマー（スタートバリア）の仕組み

負荷コンテナを docker run -d で順に起動しても、コンテナ起動とスクリプト読み込みに数秒のばらつきが出る。ずれたまま走ると「先に始まった言語だけ空いているCPUを使えた」という不公平が生じる。言語が8本に増えると、最初と最後の起動差は無視できない大きさになる。

1. オーケストレータが「現在時刻 + 15秒」を epoch ミリ秒で確定する
2. 全ての k6 コンテナに同じ値を START_AT 環境変数で渡して起動する
3. 各 k6 は setup() でその時刻までミリ秒精度で待機する
4. 全員が同一の壁時計時刻で一斉に負荷を開始する
5. オーケストレータは docker wait で全本数の終了を待ち、資源サンプラを止める

猶予（--barrier）は起動する言語数に応じて伸ばす。8言語なら 15 秒が既定。
コンテナ起動が猶予を超えると、遅れた言語だけ負荷開始が欠ける。

5.4 資源使用量の計測

docker stats を1秒間隔でポーリングし、コンテナごとの CPU%・メモリ・ネットワークIO を CSV に落とす。

cAdvisor + Prometheus を使わない理由

監視スタックのほうが精緻だが、監視スタック自身がホストのCPUを消費して計測対象を歪める。本ベンチマークは「同じホスト上で公平に比べる」ことが目的なので、観測コストが最小の手段を選んだ。より高精度な計測が必要になった時点で差し替える。

6. 実行場所の分離

工程実行場所
設計、コード記述、ロジック一致テスト（make test）クラウドセッション可（Docker不要）
イメージビルド、負荷計測、レポート生成PC実機 / VPS のみ

クラウドセッションのコンテナは CPU 割当が共有かつ変動し、Docker デーモンも常用できない。そこで出した数値は再現性がなく、言語選定の根拠にできない。

7. 品質保証

7.1 パリティ検証（性能計測の前提条件）

計算ロジックは HTTP 層から切り離し（core.py / score.go / core.rb / core.ts / Score.java / Score.cs / Score.php / score.rs）、Python 実装を基準として tests/golden.json に期待値を固定する。他7言語のテストはこのファイルと完全一致することを検証する。

  • make test — Docker 不要。全8言語のロジック一致を検証する。コード変更時は必ず実行。
  • make test-quick — ホストに入っている言語だけ検証し、欠けている言語を「未検証」として明示する。8言語のツールチェーンがローカルに揃っていない場合はこちら。
  • make verify — 実際に起動した8サービスへ同一リクエストを投げ、応答の一致を検証する。計測の直前に実行。

未検証を黙って飛ばさない

make test-quick はツールチェーンの無い言語を SKIP するが、SKIP した言語を必ず名前付きで報告する。黙って飛ばすと「テストが通った」と誤解して壊れた実装のまま計測に進む。8言語すべての検証は CI が担保する。

7.3 CI による自動検証

.github/workflows/lang-bench.yml が PR ごとに以下を自動で検証する。ローカルに8言語のツールチェーンが揃っているのは稀なので、全言語での検証はここが唯一の場になる。

  1. 期待値ファイルの鮮度 — gen_golden.py を再実行して tests/golden.json に差分が出ないことを確認する。Python 実装を変えたのに再生成し忘れると、他言語だけが古い期待値と比較され続けるため。
  2. 全8言語のロジック一致 — 8つのツールチェーンを用意して run_tests.py を実行する。SKIP が1つでも出たら失敗させる（CI 側の不備であり、見逃すとその言語だけ未検証のまま緑になる）。
  3. Compose 定義の妥当性 — docker compose config が通ること。
  4. リソース上限の均一性 — 全サービスの cpus と mem_limit が完全に一致することを機械的に確認する。公平性の根幹なので目視に頼らない。

7.2 ブラウザからの実行テスト

make console で http://localhost:18080 にコンソールを起動し、ブラウザから疎通確認・パリティ検証・簡易スループット測定を行う。8サービスは nginx リバースプロキシで同一オリジン配下に置き、CORS 設定を計測対象サーバに足さずに済ませている。

8. 受け入れ基準

  1. CI（lang-bench parity）が緑であること。全8言語のロジック一致とリソース上限の均一性が自動検証される。
  2. make test が8言語すべてで通ること（ロジック一致）。
  3. make verify が通ること（起動中の8サービスの応答一致）。
  4. ブラウザコンソールの「ヘルスチェック」「パリティ検証」が8言語すべて OK になること。
  5. make bench が isolated / concurrent の両方を完走し、results/<日時>/report.html が生成されること。
  6. レポートに RPS・p50・p95・最大・失敗率・スパイクp95・CPU平均・メモリ最大が8言語分そろい、n/a が無いこと。
  7. 負荷シナリオの閾値（定常時 失敗率 < 1%、p95 < 1000ms）に対する各言語の合否が判定できること。

10. 想定リスクと対処

リスク対処
ホストで別の重い処理が動いていて数値が汚れる計測前に他のコンテナ・重いアプリを停止する。manifest.json にホスト論理CPU数を記録し、条件が違う結果同士を比較しない。
負荷元（k6）がボトルネックになり、言語差が潰れるCPU使用率を確認し、k6 が飽和しているなら VU を下げるか負荷元を別ホストに出す。
実装のロジックがいつの間にかずれるゴールデンテストで機械的に検出し、CI で PR ごとに強制する。仕様変更時は8実装を同時に直し make golden で期待値を再生成する。
言語が増えて同時実行がホストの容量を超える8言語 × 2CPU = 16スレッド分を要求する。ホストが足りない場合は --langs で対象を絞るか、BENCH_CPUS を下げて全言語で揃える。一部だけ下げてはいけない。
Java / C# が 512MB 上限に収まらない起動失敗やGC過多になる。BENCH_MEMORY を上げて全言語で同じ値にしてから測り直す。
1回の結果を過信する同条件で最低3回実行し、ばらつきの幅を確認してから判断する。
結果ファイルが肥大化するresults/ は .gitignore 済み。共有する結果は report.html のみ個別に取り出す。
