要件定義 — Python / Go / Ruby 性能比較ベンチマーク

プロジェクト: portfolio/projects/38_lang_bench ／ 仕様ID: SPEC-API-v1 ／ 作成日: 2026-09-02

1. 背景と目的

商用サービスのバックエンド言語を Python / Go / Ruby から選定するにあたり、「どれが速いか」という一般論ではなく、自分たちのワークロードで、自分たちのサーバ上で、どれだけの差が出るかを数値で押さえたい。

本プロジェクトは、3言語に完全に同一の業務処理を実装し、同一のリソース上限を課したDockerコンテナ上で、同一の負荷シナリオを流して比較する計測基盤である。

このベンチマークで答えたい問い

  1. 同じCPU割当で、各言語は毎秒どれだけの注文を捌けるか（スループット）
  2. 応答時間の裾（p95 / 最大）はどこまで伸びるか（SLA設計の根拠）
  3. 突発トラフィック時にどう劣化するか（スパイク耐性）
  4. 同じ処理量あたりのCPU・メモリ消費はどれだけ違うか（サーバ単価）
  5. 1台のホストに3サービスを同居させたとき、どの言語が最も崩れにくいか（集約適性）

2. スコープ

区分内容
対象HTTP JSON API サーバとしての性能。CPU計算・JSON入出力・メモリ確保・並行処理を1リクエストに束ねた複合ワークロード。
対象外データベースI/O、外部API呼び出し、WebSocket、バッチ処理、開発生産性・保守性・採用のしやすさ。
※これらは言語選定の重要な判断材料だが、本ベンチマークの計測対象ではない。
実行環境Docker / Docker Compose v2 が動作する PC 実機または VPS。クラウドセッション上では実測しない（下記 6章）。

3. 計測対象アプリケーション仕様（SPEC-API-v1）

3言語はこの仕様に完全準拠し、同一入力に対して lang フィールドを除き1バイトも違わない応答を返さなければならない。片方だけ手を抜いていれば速いのは当然で、数値の意味が失われるため。

3.1 エンドポイント

メソッド / パス役割
POST /api/v1/score本計測対象。注文のスコアリング処理。
GET /healthz起動完了判定。Docker HEALTHCHECK とベンチ開始待ちに使う。
GET /metrics処理済み件数とワーカー情報。動作確認用。

3.2 リクエスト / レスポンス

// リクエスト
{
  "order_id": "ORD-1000001",
  "items": [ { "sku": "SKU-0001", "qty": 3, "unit_price": 1200.55 }, ... ],
  "customer": { "tier": "gold", "history_days": 400 },
  "rounds": 200
}

// レスポンス（200）
{
  "order_id": "ORD-1000001", "lang": "go", "item_count": 3,
  "subtotal": 4016.64, "discount": 602.5, "tax": 341.41, "total": 3755.55,
  "signature": "ea47560f…", "top_skus": ["SKU-0001","SKU-0003","SKU-0002"], "rounds": 200
}

3.3 処理手順（この順序と計算式を3言語で完全に揃える）

  1. JSONデシリアライズ — フレームワークの自動バリデーションは使わず、3言語とも手動で解釈する。
  2. バリデーション — order_id 非空、items 非空、全明細で qty > 0 かつ unit_price ≧ 0。違反は 400 validation_failed。
  3. 金額計算 — subtotal = Σ(qty × unit_price) を小数第2位で丸める。
  4. 割引率 — gold 0.12 / silver 0.07 / その他 0.02。history_days ≧ 365 なら +0.03。上限 0.20。
  5. 税・合計 — tax = (subtotal − discount) × 0.10、total = subtotal − discount + tax。各段で丸める。
  6. 署名生成（CPU負荷の本体） — SHA-256("order_id|subtotal") を初期値に、SHA-256 を rounds 回チェーンする。
  7. 上位SKU抽出 — 明細を金額降順（同額は SKU 昇順）でソートし上位5件。
  8. JSONシリアライズして返す。

丸めに関する厳守事項

丸めは「0.5 は絶対値の大きい側へ」で統一する。Python の組み込み round() は偶数丸め（バンカーズ丸め）であり、そのまま使うと Go / Ruby と金額が食い違う。Python 側は math.floor(x*100+0.5)/100 で明示的に揃えること（services/python/core.py の round2()）。

3.4 負荷の可変パラメータ

パラメータ効果既定値
roundsSHA-256 の反復回数。上げるほどCPU比重が増す。200
items1注文あたりの明細数。上げるほどJSONパース／メモリ確保／GC比重が増す。12
vus同時接続数。上げるほど並行処理モデルの差が出る。50

この3つを振ることで、「CPU寄りの処理」「JSON寄りの処理」「高並行の処理」それぞれで言語の得手不得手を切り分けられる。

4. 実行環境の要件

4.1 各言語の構成

言語ランタイムWebサーバ構成並行モデル
Python3.12-slimFastAPI + uvicorn（プロセス2）async I/O + マルチプロセス（GIL回避）
Go1.22（静的バイナリ / alpine）標準 net/httpgoroutine（GOMAXPROCS=2）
Ruby3.3-slim（YJIT 有効）Sinatra + Puma（プロセス2 × スレッド8）マルチプロセス + スレッド（GVL制約あり）

いずれも「その言語で商用APIを書くなら普通こうする」という構成を選んだ。最速化のためのチューニング（Cアクセラレータ、代替JSONライブラリ等）は意図的に入れていない。素の状態での比較を目的とするため。

4.2 公平性の担保（これを崩すと計測が無意味になる）

  • リソース上限を3コンテナで完全に揃える。 cpus: 2.0 / mem_limit: 512m。揃えないと言語差ではなくホストの空き資源差を測ることになる。
  • ワーカー並列度を揃える。 Python workers=2、Go GOMAXPROCS=2、Ruby workers=2。
  • ウォームアップを必ず挟む。 JIT / YJIT / コネクションプール / ページキャッシュが温まる前の数値は捨てる。
  • 負荷元はコンテナ名で直接叩く。 ホストの公開ポート経由にすると docker-proxy がボトルネックになり、言語差ではなくポートフォワードの詰まりを測ることになる。
  • ペイロードは固定シードで事前生成する。 負荷元のリクエスト生成コストが計測に混ざらないようにする。
  • ブラウザ用コンソール（nginx）は計測時に起動しない。 Compose の profiles: ["tools"] で分離する。

5. 計測設計

5.1 負荷フェーズ（1回の実行につき3段）

フェーズ内容目的
warmup（既定15秒）VU = 定常の1/5ランタイムを温める。集計対象外。
steady（既定60秒）VU 固定（既定50）本計測。言語間比較の主データ。
spike（25秒）VU を 4倍まで急増させ戻す飽和時の劣化の仕方を見る。

5.2 実行モード（2種類。両方を1回の run で回す）

モードやること読み取れること
isolated1言語ずつ単独で起動して負荷をかける。計測対象以外のコンテナは停止する。その言語の素の性能。言語選定の主データ。
concurrent3言語を同時起動し、共通の壁時計時刻（スタートバリア）で3本の負荷を一斉に開始する。ホストCPUを奪い合う状況での劣化幅。1台に複数サービスを同居させる構成の適性。

concurrent の数値は isolated より必ず悪くなる。単独の絶対値だけを見ても本番の挙動は分からず、同時実行だけを見ても言語の素の力は分からない。両者を並べて初めて意思決定に使える。

5.3 同時実行タイマー（スタートバリア）の仕組み

3本の負荷コンテナを docker run -d で起動しても、コンテナ起動とスクリプト読み込みに数秒のばらつきが出る。ずれたまま走ると「先に始まった言語だけ空いているCPUを使えた」という不公平が生じる。

1. オーケストレータが「現在時刻 + 8秒」を epoch ミリ秒で確定する
2. 3本の k6 コンテナすべてに同じ値を START_AT 環境変数で渡して起動する
3. 各 k6 は setup() でその時刻までミリ秒精度で待機する
4. 全員が同一の壁時計時刻で一斉に負荷を開始する
5. オーケストレータは docker wait で3本の終了を待ち、資源サンプラを止める

5.4 資源使用量の計測

docker stats を1秒間隔でポーリングし、コンテナごとの CPU%・メモリ・ネットワークIO を CSV に落とす。

cAdvisor + Prometheus を使わない理由

監視スタックのほうが精緻だが、監視スタック自身がホストのCPUを消費して計測対象を歪める。本ベンチマークは「同じホスト上で公平に比べる」ことが目的なので、観測コストが最小の手段を選んだ。より高精度な計測が必要になった時点で差し替える。

6. 実行場所の分離

工程実行場所
設計、コード記述、ロジック一致テスト（make test）クラウドセッション可（Docker不要）
イメージビルド、負荷計測、レポート生成PC実機 / VPS のみ

クラウドセッションのコンテナは CPU 割当が共有かつ変動し、Docker デーモンも常用できない。そこで出した数値は再現性がなく、言語選定の根拠にできない。

7. 品質保証

7.1 パリティ検証（性能計測の前提条件）

計算ロジックは HTTP 層から切り離し（core.py / score.go / core.rb）、Python 実装を基準として tests/golden.json に期待値を固定する。Go と Ruby のテストはこのファイルと完全一致することを検証する。

  • make test — Docker 不要。3言語のロジック一致を検証する。コード変更時は必ず実行。
  • make verify — 実際に起動した3サービスへ同一リクエストを投げ、応答の一致を検証する。計測の直前に実行。

7.2 ブラウザからの実行テスト

make console で http://localhost:18080 にコンソールを起動し、ブラウザから疎通確認・パリティ検証・簡易スループット測定を行う。3サービスは nginx リバースプロキシで同一オリジン配下に置き、CORS 設定を計測対象サーバに足さずに済ませている。

8. 受け入れ基準

  1. make test が3言語すべてで通ること（ロジック一致）。
  2. make verify が通ること（起動中の3サービスの応答一致）。
  3. ブラウザコンソールの「ヘルスチェック」「パリティ検証」が3言語すべて OK になること。
  4. make bench が isolated / concurrent の両方を完走し、results/<日時>/report.html が生成されること。
  5. レポートに RPS・p50・p95・最大・失敗率・スパイクp95・CPU平均・メモリ最大が3言語分そろい、n/a が無いこと。
  6. 負荷シナリオの閾値（定常時 失敗率 < 1%、p95 < 1000ms）に対する各言語の合否が判定できること。

10. 想定リスクと対処

リスク対処
ホストで別の重い処理が動いていて数値が汚れる計測前に他のコンテナ・重いアプリを停止する。manifest.json にホスト論理CPU数を記録し、条件が違う結果同士を比較しない。
負荷元（k6）がボトルネックになり、言語差が潰れるCPU使用率を確認し、k6 が飽和しているなら VU を下げるか負荷元を別ホストに出す。
3実装のロジックがいつの間にかずれるゴールデンテストで機械的に検出する。仕様変更時は3実装を同時に直し make golden で期待値を再生成する。
1回の結果を過信する同条件で最低3回実行し、ばらつきの幅を確認してから判断する。
結果ファイルが肥大化するresults/ は .gitignore 済み。共有する結果は report.html のみ個別に取り出す。
